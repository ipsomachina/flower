Derived values and aggregates

A derived value is a computation the engine caches and keeps correct. It records exactly what each evaluation read, and drops the cached result when any of it changes — present rows, absent keys and empty ranges included.

Derived values

#[derived] adapts a function taking a DerivedCtx. A derived context can read collections, indexes, other derived values and the clock — nothing else: no writes, no calls to methods, no identity. An instance is identified by the definition name plus its canonical arguments:

Like #[query], the attribute keeps the function and adds an argument struct (UnshippedArgs) and a static named after it in upper case (UNSHIPPED, a Derived), which you list among the app's components. Its options are name, export (other modules may read it) and materialize (below); a derived value is never called over HTTP directly — queries read it.

Read it from any context with ctx.get_derived(module, name, &args), where "" is your own module. Reading a derived value makes it a dependency of the reader, so a query reading unshipped is itself invalidated when unshipped changes.

How the engine keeps a derived value correct:

  • Dependencies are observed, not declared. Every key read (found or absent), every scan and every index range read becomes an edge. A write that touches any of them drops the cached outcome; a write that touches none of them leaves it alone.
  • Outcomes include errors. A failed evaluation is cached too, with the old and new dependencies, so the change that fixes it re-evaluates it.
  • Mutations see fresh values. Inside a mutation, a derived value read after the mutation's own writes reflects them.
  • New code invalidates everything it computed. Every activation of a module starts a new code era: values computed by earlier code are re-evaluated on their next read.
  • Evaluation nests at most 16 deep; a dependency cycle fails as a guest failure.

Materialization

By default an instance is computed on demand and kept in cache while there is room (Materialize::Never). A materialized instance is a pinned root: when its dependencies change it is re-evaluated eagerly, at commit, so reads never pay for it. Set the policy in the attribute or on the descriptor:

  • #[derived(materialize = always)], or .materialize(Materialize::Always) on a Derived static, pins every evaluated instance.
  • #[derived(materialize = each(Orders))], or .materialize(Materialize::Each(Orders::raw())), keeps one root per row of a collection of the same module, at arguments {"key": <row key>}: inserting a row pins its root, deleting it unpins it.
  • ctx.materialize(module, name, &args) and ctx.unmaterialize(…) in a mutation pin and unpin individual instances by hand.

Aggregates

An aggregate keeps one accumulator per group of an index, and maintains it by deltas: a write folds the changed row's old image out and its new image in, without reading the group's other rows again. Implement index::TypedAggregate:

On the node from the quickstart, with two orders for ada and then one of them reassigned to bob:

{"ok":true,"value":{"cents":2050,"orders":2}}    // totals for ada
{"ok":true,"value":{"cents":800,"orders":1}}     // ada, after the move
{"ok":true,"value":{"cents":1250,"orders":1}}    // bob
  • Group is a full prefix of the index fields: the aggregate groups by every field of the index you name. Declare an index with exactly the fields you want to group by.
  • The first read of a group builds it by folding its rows through add in index order, a page (PAGE, 256 rows) at a time. After that, writes update it incrementally, in the writing transaction.
  • remove must be the exact inverse of add, and both must be order-independent: changes arrive in key order, not write order. Use integers (cents, not floating-point euros). Returning Ok(None) from remove — its default, for things like a minimum that cannot take a row out — makes the engine rebuild that group from its rows.
  • The reducer runs without a context: add and remove cannot read anything else (aggregate_context_forbidden).
  • VERSION lets cached groups survive a redeployment that keeps the same version, collection, index and fields. Without one, new code rebuilds every group it reaches.
  • A collection declared without types can still be a source, through a TypedCollection marker whose key and value are Value.

Read a group with CustomerTotals::get(ctx, &(customer,)), as totals does: it returns the decoded accumulator. Underneath, an aggregate is a derived value named NAME whose arguments are {"group": [<field values>]}; list its DERIVED descriptor (here with a materialization policy) among the app's components.

Triggers and retention hooks

A trigger runs inside the mutation that changed its source collection, once per net change of a row, with the row's key and its image before and after:

  • Triggers fire when the mutation settles — at an explicit ctx.settle() or at commit — exactly once per (collection, key, after-image). The before-image is the committed row, unaffected by the mutation's own staged writes.
  • Each firing runs under its own savepoint with the module's rights. A failing trigger rolls back its own writes and fails the mutation.
  • Triggers and reference cascades that trigger each other abort after 16 rounds with cascade_too_deep.
  • The engine fires a trigger as a mutation of the trigger's name, which is why cargo flower build counts it among the mutations.

A retention hook (features::TypedRetention, whose RETENTION descriptor you list among the app's components) is different: it sees every successful deletion of a row, with the deleted value and time, so it can archive or keep data that would otherwise disappear. A delete followed by a re-insert is no net change for a trigger, but it is still a deletion for retention. delete_permanently skips retention.

Maintenance tasks

A maintenance task is periodic work driven by data. due says, as a query, when the task next has work; while that moment is past, the leader runs run, one bounded unit at a time, as a replicated mutation:

  • due must depend only on data and time. Before each run the engine evaluates it again in the run's own transaction, so a unit of work never runs twice.
  • The leader checks tasks after writes, at the earliest declared due time, on leadership changes and at least every --timer-sweep-ms (one second by default). Followers never run tasks; a new leader carries on from replicated state.
  • A failed run rolls back and the task backs off — one second, doubling up to a minute — unless it sets HANDLES_FAILURES and implements on_error. Operators see each task's failures in cargo flower modules.
  • For work at a specific time, or triggered by a specific event, prefer a timer.
