Concepts

Transactions and partitions

A mutation is atomic within one database. A transaction runs mutations in several databases — in one group or across groups — and commits all of them or none.

Transactions are lists of steps

A transaction is a list of steps, each naming a database, a module, a mutation the module exposes over HTTP (method) and its arguments. Each step must target a different database. Send it to POST /v1/transaction:

curl -s http://127.0.0.1:8080/v1/transaction -H 'content-type: application/json' -d '{
  "steps": [
    {"db": "demo",    "module": "tasks", "method": "complete_task", "args": {"id": "eggs"}},
    {"db": "archive", "module": "tasks", "method": "add_task",      "args": {"id": "eggs", "title": "Buy eggs"}}
  ],
  "idempotency_key": "archive-eggs"
}'
{"ok":true,"value":[{"done":true,"title":"Buy eggs"},{"done":false,"title":"Buy eggs"}],"revision":6,"position":44,"revisions":{"archive":1,"demo":6},"duplicate":false}

value holds each step's result in order, and revisions the revision each database reached. If any step fails, nothing commits anywhere, and the answer is that step's failure, with HTTP 422 like any call's own failure:

{"ok":false,"revision":6,"position":0,"code":"TASK_EXISTS","message":"a task with this ID already exists","duplicate":false}

The same transaction from the CLI and from Rust:

cargo flower transaction \
  --steps '[{"db":"demo","module":"tasks","method":"add_task","args":{"id":"jam","title":"Jam"}},
            {"db":"archive","module":"tasks","method":"add_task","args":{"id":"jam","title":"Jam"}}]'
pub async fn archive(client: &FlowerClient, id: &str) -> Result<TransactionResult, FlowerError> {
    let steps = vec![
        TransactionStep {
            db: "demo".to_string(),
            module: "tasks".to_string(),
            method: "complete_task".to_string(),
            args: json!({"id": id}),
        },
        TransactionStep {
            db: "archive".to_string(),
            module: "tasks".to_string(),
            method: "add_task".to_string(),
            args: json!({"id": id, "title": "archived"}),
        },
    ];
    let options = TransactionOptions {
        request_id: Some(format!("archive:{id}")),
        ..TransactionOptions::new()
    };
    client.transaction(&steps, &options).await
}

What a transaction guarantees

  • All or nothing. Every step commits, or none does.
  • Steps are isolated from each other. Each step prepares in its own session against its own database; a step never sees another step's writes. Pass whatever a later step needs in its arguments.
  • Each database stays consistent. Steps are validated against the latest state of their database at commit, just like mutations. Transactions take no expected_revision.
  • Retries are safe. An idempotency_key works as for mutations: a retry answers the recorded outcome with "duplicate": true. Transactions accept only plain keys, not scoped f1:/f2: IDs.
  • Steps call what each module exposes over HTTP (http on the mutation; anything else answers 404 UNKNOWN_METHOD), under the caller's credentials, and each module's authorization hook decides as for a single call.
  • One deadline. The whole transaction — every step and everything it nests — runs under one deadline: 60 seconds, or less when the caller's x-flower-timeout-ms says so.
  • Bounded by size, not by count. There is no limit on the number of steps. What bounds a transaction is the size of what it commits: an entry larger than the operator's --max-transaction-bytes (32 MiB by default) fails with 413 transaction_too_large before anything is proposed, naming the measured and allowed sizes. The same bound applies to a single mutation's writes.

Within one group

When every database lives in the same Raft group — the usual case, since unplaced databases all live in root — the transaction commits as one log entry at one position. Watchers of each database see the change at that database's new revision.

Across groups

When the databases live in different groups, the first step's group coordinates a two-phase commit: it records the transaction durably, asks each participant group to prepare, decides, and has every participant finish. A participant persists its read and write footprint, including the transitive source dependencies behind cached derived values. Every replica checks that same footprint, even when its own derived cache differs. Independent writes can continue, including writes that store retry receipts or maintain unrelated derived values. Conflicting writes wait within their deadlines.

Timer and queue reads protect the rows and ranges they actually inspected; they do not block unrelated writes merely because they are volatile for query caching. Reads outside the snapshot (retained history or native untracked reads), cached derived values with untracked dependencies, scans over derived-cache entries, oversized footprints and older derived footprints without source proofs retain a whole-database fence. Deployments, partition freezes and a second distributed prepare of the same database still wait; the second prepare gives up after a second with transaction_conflict. Reads never wait, and never see prepared but undecided state.

  • The answer carries positions: the log position in each participant group.
  • Each group applies its part on its own, so a reader that looks at two groups in quick succession may briefly see one side committed before the other. Atomicity is about outcomes, not about a single instant of visibility across groups.
  • If the coordinator fails, participants that prepared ask it for the decision; undecided transactions in which every participant prepared commit, others abort. Operators can list and abort stuck transactions with cargo flower transactions.

Planned in the guest A module can also plan a transaction itself. Transaction::new(name, planner).args(schema) declares a raw planner, a function from the arguments to a Plan of calls; listed among the app's components and declared .http(), it answers POST /v1/mutate under its name: the planner runs under its deadline, and its calls run in one session and commit together. There is no typed-planner macro: a planner validates and encodes its arguments by hand.

Partitions

Placing a database in its own group — making it a named partition — changes where it runs, not how you call it. Clients keep naming the database; the server routes each call to the owning group. Reasons to partition:

  • Isolation. A busy tenant's writes queue on its group's leader, not on everyone's.
  • Scale. Each group has its own leader and log, so write throughput grows with groups placed on different servers.
  • Placement. A group's members can be the servers in one region.

The cost is that work spanning partitions in different groups becomes a cross-group transaction, with the locking described above. Design partitions so that most mutations touch one database.

Operators create groups and place, move and retire partitions with cargo flower group and cargo flower partition; see Operating a cluster. While a partition moves, its calls briefly answer 503 partition_moving with Retry-After: 1; after the move, the old owner answers partition_moved and the server retries at the new owner for you.
