Retries and receipts

Networks fail after a write has committed but before its answer arrives. Give each write a request ID and retry with the same one: Flower answers the original outcome instead of running the write again.

Request IDs

A mutation or transaction request may carry an idempotency_key (in the Rust client, MutationOptions::request_id; in the CLI, --request-id). When the write commits, the database stores a receipt: the outcome under that key, with its value, revision and position. A later request with the same key does not run again; it is answered from the receipt, with "duplicate": true:

{"ok":true,"value":{"done":false,"title":"Buy milk"},"revision":1,"position":4,"duplicate":false}
{"ok":true,"value":{"done":false,"title":"Buy milk"},"revision":1,"position":4,"duplicate":true}

That holds whichever member the retry reaches, and after any number of later writes. A business failure is an outcome too: a retry of a request that failed with TASK_EXISTS gets TASK_EXISTS again. If the original is still committing when the retry arrives, the retry waits for it (up to five seconds).

Retries are authorized again before they are answered: a caller whose credentials were revoked cannot read a recorded result. A receipt also remembers which principal wrote it; another principal presenting the same key gets identity_conflict.

Choose keys per intent A plain key is not checked against the request's content: reusing a key for a different call replays the first call's result. Derive keys from what the user meant to do ("order 42 of cart 7"), persist them before sending, and reuse them only for retries of that same intent. If you want the server to check, use a scoped ID.

When to retry

Retry with the same key whenever you cannot tell whether a write committed: a timeout, a dropped connection, a cancelled request, 503 leader_isolated, 503 forward_failed. Retry, with or without the key, after refusals that guarantee nothing ran: 503 overloaded (honour Retry-After), 503 quorum, 503 partition_moving and the other 503s. Never treat an HTTP 422 with "ok":false as transient: that is your method's own answer, recorded like a success. The client guide lists every case, and flower-client implements this policy for you.

How long receipts last

Every database served by cargo flower serve gets a retry window, by default 24 hours (--retry-window-ms). Receipts are grouped into epochs of one eighth of the window, and nine epochs are kept, so a write stays retryable for at least the window and at most one eighth longer — 24 to 27 hours by default — before the leader collects its receipt. Operators can change a database's retention with cargo flower retention: the epoch length, how many epochs to keep, and a byte budget beyond which new writes are refused with receipt_budget_exceeded rather than evicting anything.

A retry with a key whose receipt has been collected runs again as a new write. Design for the window: a client that might retry after a day needs its own deduplication.

Scoped request IDs

Two kinds of ID give stronger guarantees than a plain key. Both are minted from the database's current retry identity, which GET /v1/retry?db=… returns and cargo flower retry --db … prints:

  • f1: IDs are derived from a business intent: f1:<incarnation>:<epoch>:<sha-256 of the intent>. Their receipt pins the module, alias, canonical arguments and expected revision, so the same ID with different content is refused with identity_conflict. Mint one with cargo flower retry --db D id --intent order:42 or client.retry_identity(db) and RetryIdentity::request_id(intent).
  • f2: IDs belong to a retry session: a numbered sequence of writes a client opens, acknowledges as it learns their outcomes, and closes. The server can then release acknowledged receipts early, and refuses IDs older than what was acknowledged (already_acknowledged). Sessions are for clients that issue many writes and track them, such as a device draining an offline queue.

Scoped IDs are tied to the database's history. After a restore to an earlier point, the database starts a new history, and IDs minted before it are refused with wrong_history rather than silently replayed or re-run. Plain keys survive restores and partition moves.

Refusals a receipt can decide

CodeMeaning
identity_conflictThe key belongs to another principal, or a scoped ID was reused for different content.
epoch_retired / epoch_not_admittedThe scoped ID's epoch is older than the oldest kept, or from the future.
wrong_historyThe scoped ID was minted in another history of the database (before a restore).
receipt_releasedThe receipt was released by a retry session acknowledgement.
retry_session_unknown, retry_session_closed, retry_session_forbidden, already_acknowledged, retry_ack_gapRetry-session states.
receipt_budget_exceededThe database's receipt budget is full.

These are answered like a call's own failure — HTTP 422 with "ok":false — and are not duplicates:

{"ok":false,"revision":7,"position":0,"code":"identity_conflict","message":"retry identity reused with a different intent","duplicate":false}
