Databases, modules and groups

Every call names a logical database and a module. Logical databases are the unit of atomicity; modules are namespaces of code inside them; Raft groups are where databases physically live.

Logical databases

A logical database is an atomic application-state domain. It holds source records, indexes and derived values, the deployed code of its modules, its timers, queues and retry receipts, its catalog of managed keys, and one revision counter that moves with each committed change. Every HTTP call carries its name in db; every cargo flower command that touches application state takes --db.

You do not create databases explicitly. A database comes into being the first time you deploy a module into it. Names are yours to choose: one database per application, per environment, or per tenant are all reasonable.

A mutation is atomic within its database. Work spanning several databases goes through a transaction, which is atomic across all of them.

Modules

A module is one deployed Wasm artifact inside a database, under a name you choose at deploy time. The same artifact can be deployed under several names, or into several databases. Each module has its own collections, methods, derived values and HTTP names; a collection called tasks in module crm is unrelated to one called tasks in module jobs.

Modules share their database's revision and commit atomically with each other: a mutation in one module that calls an exported mutation in another commits both modules' writes in one entry. They are capability boundaries, not consensus domains. A module exports nothing unless its declarations say so (export); other modules reach it only through what it exports, and clients only through what it declares http.

The module named "" (the empty string) is the database's host module. Inside guest code, "" also means "the calling module" wherever a module name is expected, so CollectionRef::local("tasks") is CollectionRef::new("", "tasks").

Named partitions and groups

A server process can host several Raft groups. Each group has one ordered log and one leader at a time. The root group exists from bootstrap; it spans every server process and holds the partition catalog. Every database the catalog does not place lives in root.

An operator can create more groups on a subset of the servers, and place a database on one of them, which makes it a named partition. A partition is still addressed by its database name: clients never name groups. The server that receives a call looks the database up in the catalog and routes the call to the group that owns it, forwarding to that group's leader when needed. Responses for placed databases carry x-flower-group and x-flower-partition-epoch headers so you can see where a call ran.

Placement is an explicit decision, made with cargo flower group create and cargo flower partition create; Flower does not split or rebalance data on its own. Placing an existing database adopts it in place. A partition can be moved to another group while it serves: rows, code, revisions, receipts, timers and queues travel with it, and retry identities stay valid. During the brief freeze at cutover, calls answer a retryable 503 partition_moving. See Operating a cluster.

Tenants are not partitions A key containing a tenant_id does not create a partition, and several application tenants can share one database if your access rules keep them apart. Giving a tenant its own database — and possibly its own group — is a choice you make when you deploy.

Replicas, leaders and followers

Each member of a group keeps a full copy of the group's databases. The leader runs mutations and appends their accepted consequences to the log; followers apply those consequences without running guest code. Any member answers queries, according to the consistency each query declares (see Revisions and consistency), and any member accepts writes, forwarding them to the leader.
