Concepts

Queries and mutations

Methods are plain synchronous Rust functions. Queries read one snapshot; mutations read and write, and commit atomically. Each is declared once, with everything about it — its name, whether clients may call it over HTTP, who may call it, its consistency and its deadline — and an App lists them.

Queries

#[query] adapts a function whose first parameter is ctx: &mut QueryCtx<'_, '_>. The remaining parameters become the fields of the method's JSON arguments object, and the return type becomes its result contract:

/// An infallible query: the return type is the result contract.
#[query(http)]
pub fn greet(ctx: &mut QueryCtx<'_, '_>, name: String) -> String {
    let _ = ctx;
    alloc::format!("Hello, {name}!")
}

/// A fallible query returning the SDK's own `Result`, with its own
/// deadline.
#[query(http, timeout = "500ms")]
pub fn balance(ctx: &mut QueryCtx<'_, '_>, account: String) -> Result<Option<u64>> {
    let account = Accounts::get(ctx, &account)?;
    Ok(account.map(|account| account.balance))
}

/// The same callback under another name, served from any replica's own
/// state at most two seconds stale.
pub static BALANCE_NEARBY: Op<BalanceArgs, Option<u64>> = BALANCE
    .named("balance_nearby")
    .consistency(Consistency::ReplicaLocalWithin(2_000));

The macro keeps your function as it is — you can still call balance(ctx, account) from Rust — and adds two items:

  • a public argument struct named after the function (BalanceArgs, one field per parameter after ctx), which derives FlowerType: callers in Rust build it instead of writing JSON;
  • a static named after the function in upper case (BALANCE), an Op<BalanceArgs, Option<u64>, Failure>. It is the component the app lists, and it carries the method's name, kind, argument, result and error types, so timers, tests and the Rust client call it type-checked.

Arguments are checked against the struct's schema before your code runs; arguments that do not match fail with INVALID_ARGUMENT, whose details.path names the offending member. A parameter of type Option<T> is an optional member that callers may leave out. Methods must be synchronous, non-generic and free of self.

BALANCE_NEARBY shows the other way to declare an operation: .named(..) on an existing static makes a twin of the same callback under another name, here with another consistency. Definition names are unique within a module, so a twin is how one read is served two ways.

A query sees one consistent snapshot of its database. It can read collections, indexes and derived values, read the clock, learn its caller, and call other modules' exported queries. It cannot write. Query results are cached and shared: an identical query (same method, arguments and caller) at an unchanged revision is answered from a result cache, and identical queries in flight at the same time are joined into one evaluation.

Mutations

#[mutation] works the same way with a MutationCtx. A mutation can do everything a query can, plus write the module's own collections, call other modules' exported mutations, enqueue jobs, schedule timers and draw random bytes. Everything it does is staged; when it returns Ok, the engine validates the staged writes, applies their consequences (indexes, references, triggers, derived values) and commits the lot as one log entry. When it returns Err, or traps, or exceeds a budget, nothing it wrote is kept.

Mutations run on the group's leader, which prepares several at a time speculatively and commits them in order. A mutation whose reads were invalidated by an earlier one in the same batch is prepared again; you never see that, except as latency. Write mutations as if each one ran alone.

Determinism is not required Followers do not re-run your code: they apply the writes the leader's run produced. Reading the clock or drawing random bytes in a mutation is fine — the outcome is decided once, on the leader.

Options

Everything about an operation goes in its attribute, for queries and mutations alike: #[query(http, timeout = "500ms")]. All options are optional:

OptionMeaning
name = "accounts.balance"The definition's name, which is also its HTTP name. Default: the function's name.
httpCallers may reach it over HTTP under its name. Without it, no client can call it over HTTP: timer and queue handlers, trigger targets and methods written for other modules need no exposure, and none is ever public by accident.
consistency = replica_local, max_staleness_ms = 2000Queries only: how fresh a read must be. Linearizable by default. See Revisions and consistency.
access = public, authenticated or a check function's pathWho may call it, decided by the module's authorization component. Default: the component's default.
export, callers("shop", ...)Other modules of the database may call it: all of them, or only those named. Private by default. See Modules and interfaces.
timeout = "500ms"The method's own deadline (ms, s or m). Default: the operator's default, 5 s. See Deadlines and limits.
rename_all = "camelCase"The argument members' wire names in camelCase (lifetimeSeconds for lifetime_seconds), for clients speaking JavaScript conventions.
bare_argThe only parameter after ctx is the whole argument (a string, a tuple, a struct) rather than one member of an arguments object.

Raw descriptors take the same options as builder methods — Method::query(name, callback).http().access(..).export().timeout_ms(500) — for code the attributes cannot express.

Declared errors

A method that can fail returns Result<T, E> where E is either the SDK's Failure (via the flower_sdk::Result<T> alias, as in the quickstart) or an enum deriving FlowerError. Every variant names a stable code; a single payload travels as the failure's details:

/// The failures `transfer` declares. Codes discriminate the variants; a
/// payload travels as the failure's `details`.
#[derive(FlowerError, Clone, Debug, PartialEq)]
pub enum TransferError {
    #[flower(code = "ACCOUNT_NOT_FOUND", message = "no account has this ID")]
    NotFound(String),
    #[flower(code = "INSUFFICIENT_FUNDS", message = "the balance is too low")]
    InsufficientFunds(u64),
    #[flower(code = "ACCOUNT_LOCKED", retryable)]
    Locked,
    /// Every other failure (a codec, the host): `?` converts into it.
    #[flower(other)]
    Host(Failure),
}

#[mutation(http)]
pub fn transfer(
    ctx: &mut MutationCtx<'_, '_>,
    from: String,
    to: String,
    amount: u64,
) -> core::result::Result<u64, TransferError> {
    let mut source = Accounts::get(ctx, &from)?.ok_or(TransferError::NotFound(from.clone()))?;
    let mut target = Accounts::get(ctx, &to)?.ok_or(TransferError::NotFound(to.clone()))?;
    if source.balance < amount {
        return Err(TransferError::InsufficientFunds(source.balance));
    }
    source.balance -= amount;
    target.balance += amount;
    Accounts::set(ctx, &from, &source)?;
    Accounts::set(ctx, &to, &target)?;
    Ok(source.balance)
}

Over HTTP, a method's own failure answers 422, for queries and mutations alike, with "ok":false, the code, the variant's message (its name when it sets none) and the payload as details. A mutation's answer also carries the revision and log position its failed outcome was recorded at:

HTTP/1.1 422 Unprocessable Entity

{"ok":false,"revision":0,"position":12,"code":"ACCOUNT_NOT_FOUND","message":"no account has this ID","details":"a","duplicate":false}

Arguments the method's schema refuses never reach your code. They answer 422 too, with the path of the member at fault:

{"code":"INVALID_ARGUMENT","details":{"path":["account"]},"message":"arguments for `balance` invalid at $.account: expected string","ok":false}

Things to know about errors:

  • Codes are UPPER_SNAKE_CASE; the derive refuses anything else at compile time. Flower's own codes for its own failures are lowercase (deadline_exceeded, overloaded), so the two never collide.
  • One variant may be #[flower(other)] over Failure: it takes every failure that is not one of yours (a codec, the host), so ? works on SDK calls through the generated From<Failure>. Without one, convert with map_err.
  • #[flower(retryable)] marks a variant safe to retry and feeds the generated is_retryable() helper, which clients decoding the error can use.
  • The error type is part of the method's contract: other modules importing it, and Rust clients calling it through its descriptor, decode exactly these codes. See Errors and retries in clients.
  • Infrastructure failures — storage errors, overload, an unknown method — have their own codes and statuses and are never confused with yours; see Error codes and limits.

The App assembly

Nothing is discovered automatically. A module is exactly what its App static lists, in one flat list of components:

pub static APP: App = App::new(&[&Accounts, &GREET, &BALANCE, &BALANCE_NEARBY, &TRANSFER]);
ComponentListed as
Queries, mutations and derived valuesThe statics their attributes declare (&BALANCE), twins (&BALANCE_NEARBY) and raw Methods.
CollectionsThe #[collection] marker itself (&Accounts).
Aggregates, triggers, maintenance tasks, retention hooksTheir Derived, Trigger, Task and Retention statics.
QueuesA TypedQueue static: it declares a queue the module uses.
The authorization componentAn Authorization static, at most one per module.
Managed keysEach KeyDeclaration.
Imports and interface providersAn interface handle (InventoryApi::import("$inventory")), a provider's COMPONENT, an external! value.
GroupsA static array of components, to share one list between apps.

The manifest — definitions, HTTP names, exports, per-method access, queues and keys — is generated from these declarations. App::new(..).init(f) adds an optional fn() -> Result<()> run once when the server prepares the module's image, with no context; its memory and statics become the starting point of every call. Then end the crate with flower_sdk::export!(APP);.

Statics are configuration, not state Every call starts from the module's initialized image: changes a call makes to statics or the heap are gone when it returns. Keep state in collections.

Calling other modules

A method can call another module's exported methods in the same database. The call runs in the same transaction and snapshot, with the callee's module identity; the callee sees your module as its caller.

/// Pay through the `bank` module's exported `transfer`, turning its
/// declared failures into an answer instead of failing the whole call.
/// `TransferArgs` is the argument struct `#[mutation]` derived for
/// `transfer`.
#[mutation]
pub fn pay(ctx: &mut MutationCtx<'_, '_>, from: String, amount: u64) -> Result<String> {
    let args = TransferArgs {
        from,
        to: String::from("merchant"),
        amount,
    };
    let outcome = match ctx.try_mutation("bank", "transfer", &args.encode()?) {
        Ok(outcome) => decode_outcome::<u64, TransferError>(outcome)?,
        Err(CallError::Host(failure)) => return Err(failure),
    };
    Ok(match outcome {
        CallOutcome::Success(left) => alloc::format!("paid; {left} left"),
        CallOutcome::Failure(TransferError::InsufficientFunds(balance)) => {
            alloc::format!("declined: balance {balance}")
        }
        CallOutcome::Failure(other) => alloc::format!("declined: {other:?}"),
    })
}

/// Read another module's exported query. A failure here fails the
/// whole invocation, even if the caller ignores the `Err`.
#[query]
pub fn merchant_balance(ctx: &mut QueryCtx<'_, '_>) -> Result<Value> {
    let mut args = alloc::collections::BTreeMap::new();
    args.insert(
        String::from("account"),
        Value::String(String::from("merchant")),
    );
    ctx.call("bank", "balance", &Value::Object(args))
}
  • call (queries) and call_mutation (mutations) are ordinary calls: if the callee fails, your whole invocation fails, even if you handle the Err. The engine poisons the invocation so a half-done callee can never commit.
  • try_call and try_mutation run the callee under a savepoint. A recoverable failure rolls back only the callee's writes and comes back as CallOutcome::Failure; typed::decode_outcome turns it into your declared error type. Exhausted budgets and other fatal failures still fail the invocation, as CallError::Host.
  • typed::call_typed encodes typed arguments and decodes the result of an ordinary call.
  • An unknown method, a non-exported one (MODULE_PRIVATE) or invalid arguments are deterministic and have no effects, so they recover even without a savepoint.

For calls between separately built modules, an interface crate gives both sides typed handles generated from one trait.

Who is calling

Query and mutation contexts implement MethodCtx, which adds two reads:

  • ctx.principal() — the Principal the call runs as (subject, optional tenant, optional claims), or None for an anonymous call. It is decided by the module's authorization hook.
  • ctx.caller() — the calling module's name for a nested call, or None when the call came from outside.

Deadlines and limits

A method's budget is a deadline, stated where it is meant. Each call runs under the method's own timeout — or the operator's default, 5 seconds — capped by the operator's ceiling (60 seconds by default). A caller can only shorten it, by sending x-flower-timeout-ms (the Rust client always does). Everything the call nests shares that one deadline.

The engine derives the call's internal instruction and host-operation budget from the method's declaration (or a fixed default) alone, so whether a call fits does not depend on which member runs it or how that member is configured. Running out fails the call with deadline_exceeded (or budget_exhausted for the derived budget): the call's own failure, answered 422, which retrying will not fix — declare a longer timeout or do less per call. When the caller's shorter deadline passes first, the answer is caller_deadline_exceeded, 503, which an attempt with more time may get past.

The other limits are fixed: 128 MiB of memory per instance and 1 GiB across the call, and 32 levels of nesting (out_of_memory, stack_overflow, nesting_too_deep). None of these failures can be caught with a savepoint. See limits.
