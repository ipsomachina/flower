Concepts

Watches

A watch keeps one query's result up to date. You subscribe to a query and its arguments; the server sends the current value, then a new value — or a patch — whenever a commit changes what the query returns.

Subscribing

A watch is a POST /v1/watch whose body is exactly a query's — db, module, name, args, and optionally credentials — answered as server-sent events:

curl -sN http://127.0.0.1:8080/v1/watch -H 'content-type: application/json' \
  -d '{"db":"demo","module":"tasks","name":"open_tasks","args":{}}'
event: snapshot
data: {"revision":3,"id":1,"value":[{"id":"bread","title":"Bake bread"}]}

event: snapshot
data: {"revision":4,"id":3,"value":[{"id":"eggs","title":"Buy eggs"},{"id":"bread","title":"Bake bread"}]}

event: snapshot
data: {"revision":5,"id":4,"value":[{"id":"eggs","title":"Buy eggs"}]}
  • The first event is always a snapshot of the current value. Then each change to the result produces one event carrying the revision it was computed at, and an id naming the value.
  • With "deltas":true in the body, a change may arrive as a patch: an RFC 6902 JSON Patch (add, remove, replace) against the value whose id is base — always the last one delivered. Patches are sent only when smaller than the whole value: 
    event: patch
data: {"revision":4,"id":3,"base":2,"patch":[{"op":"add","path":"/0","value":{"id":"eggs","title":"Buy eggs"}}]}

event: patch
data: {"revision":5,"id":4,"base":3,"patch":[{"op":"remove","path":"/1"}]}
  • A watch that cannot start answers like the query would, with an ordinary error response: 404 UNKNOWN_METHOD for a name the module does not expose over HTTP, 403 when the authorization hook refuses, 422 when the query itself fails, 400 for a body that is not a query's (args is required; send {}).
  • Once streaming, an error event ({"code","message"}, plus details when the query's own failure carries them) ends the stream. Reconnect, unless the code says you should not (unauthorized).
  • An idle stream gets a : watching comment every 15 seconds, to keep proxies from closing it.
  • Credentials go in the body's credentials member, as for a query, or in an Authorization: Bearer header, which reaches the hook as {"bearer": token}. The module's authorization hook runs before the first snapshot.
  • The request's deadline (x-flower-timeout-ms) bounds the first snapshot only, and a trusted gateway's timestamp_ms likewise: later refreshes run on the serving member's clock, without a deadline from the request, and are shared with other subscribers.

From Rust, flower-client wraps all of this in typed, reconnecting subscriptions; see Calling Flower from Rust.

When a watch wakes

Each evaluation of the query produces a dependency certificate: the records it read (present or absent), the scan and index ranges it covered (so an insertion into an empty range counts), and the derived values it read, expanded transitively. A commit wakes a watch only if it touched something in that certificate, or changed the module's code. Unrelated writes cost one check against the change journal.

A woken watch re-evaluates its query and publishes only if the result's bytes changed. Values never go back in revision; several commits in quick succession may be coalesced into one event. Time also wakes watches: at an instant the query declared with changes_at, or every 250 ms for a query that read now(). See Time.

Watches on the same query, arguments and principal share one evaluation per member, however many clients subscribe. Access is never shared: every subscriber is authorized separately.

Reauthorization

Every delivery is authorized at the revision it shows. Before publishing a refresh, the server re-runs each subscriber's authorization against the same view it evaluates the query on. It also rechecks when a commit touches what the decision read, at the decision's declared expiry, when a managed key the decision used changes, and at least every 30 seconds. A subscriber who is no longer allowed gets an error event with code unauthorized, and the stream ends; one whose principal changed gets watch_scope_changed and should reconnect.

Consistency and failover

A watch's first snapshot reads as the query declares. Watches take no staleness bound from the caller. A follower cut off from its leader keeps its watches open but cannot refresh them, except replica-local watches with a bound, which it ends once they are past it. When a stream ends — leader change, member shutdown (shutdown), partition move, redeployment removing the alias (UNKNOWN_METHOD) — reconnect and you get a fresh snapshot.

Not an event log A watch delivers the current value of a query, not the history of changes. Reconnecting does not replay what you missed; there is no Last-Event-ID. If you need every change, write changes to a collection (a trigger is a good place) and watch or page that.

Limits

  • Each subscriber has a 32-event queue. A subscriber that falls that far behind is dropped and its stream closes without an error event; reconnect.
  • A query that reads more than 4,096 dependencies gets a broad certificate: any change to its database wakes it. Keep watched queries focused.
  • Each watch is an HTTP/2 stream. The Rust client opens another connection per 100 watches.
  • A member holds at most 64 MiB of watches' arguments and credentials. Past that, a new watch is refused as an overload (503, retryable) until others end.
