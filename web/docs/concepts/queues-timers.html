Concepts

Queues and timers

Guests never touch the outside world. Work that must — sending email, calling a payment provider — becomes a durable job that a native worker claims under a fenced lease. Work that must happen later becomes a timer that fires a mutation.

Queues

A mutation enqueues a job: a JSON payload in a named queue. The enqueue is part of the mutation, so the job exists exactly when the mutation commits and never if it rolls back. Workers then claim jobs, do the work, and report the outcome. A TypedQueue<P, R> static is the queue's declaration, its contract and its handle at once: listed among the app's components, it declares the queue, and the server checks every payload against P and every kept result against R:

#[derive(FlowerType, Clone, Debug, PartialEq)]
pub struct Email {
    pub to: String,
    pub subject: String,
}

#[derive(FlowerType, Clone, Debug, PartialEq)]
pub struct Sent {
    pub message_id: String,
}

/// The queue, its contract and its handle in one declaration. Listed
/// among the app's components, it declares the queue: the host refuses
/// any other payload, from guests and native workers alike, and checks
/// kept results too.
pub static MAIL: TypedQueue<Email, Sent> = TypedQueue::new("mail");

/// Queue an invitation in the tenant's scope. The job exists exactly
/// when this mutation commits; naming it makes a second invitation to
/// the same address fail `JOB_EXISTS` instead of queueing twice.
#[mutation(http)]
pub fn invite(ctx: &mut MutationCtx<'_, '_>, tenant: String, to: String) -> Result<String> {
    let email = Email {
        to: to.clone(),
        subject: String::from("You are invited"),
    };
    let options = EnqueueOptions::default()
        .scope(&tenant)
        .named(&format!("invite:{to}"))
        .max_attempts(10);
    MAIL.enqueue(ctx, &email, &options)
}

/// Whether an invitation went out, from the result the worker kept.
#[query(http)]
pub fn invitation_sent(ctx: &mut QueryCtx<'_, '_>, tenant: String, to: String) -> Result<bool> {
    let name = format!("invite:{to}");
    let job = Job::Named {
        scope: &tenant,
        name: &name,
    };
    Ok(MAIL.result(ctx, job)?.is_some())
}

Calling invite twice for the same address shows the named job at work. The second call is the mutation's own failure, HTTP 422:

{"ok":true,"value":"1ff7d39fc385f5fe1d53b0e5a4ca7e32","revision":5,"position":34,"duplicate":false}
{"ok":false,"revision":5,"position":35,"code":"JOB_EXISTS","message":"job invite:ada@example.com already exists","duplicate":false}

Guest code uses only the queues its own module declares; naming any other fails with queue_undeclared. A queue's work belongs to the modules that declare it: when a removed module's data is purged, the queues no other module declares are deleted with it, and until that purge ends every operation on them is refused with queue_purging, changing nothing — retry once it is over. Below the typed handle, Queue::enqueue(ctx, "mail", payload, &options) and its siblings take the queue's name and raw Values, under the same rule; a QueueDef static declares a queue with explicit schemas for that layer.

Enqueue options

OptionDefaultMeaning
scope(s)""A logical partition of the queue — per tenant, per region. Workers claim from one scope at a time. Scopes separate work; they do not authenticate anyone.
priority(p)0Lower values are claimed first.
group(g)noneWithin a priority, each ready group's next job goes before any group's second: fair turns between, say, customers.
named(n)random IDA name unique within the scope. A second enqueue of a pending or claimed name fails JOB_EXISTS.
replace()offWith a name: replace a completed or dead job of that name instead of failing.
delay_ms(d) / at_ms(t)nowNot claimable before then; at most 30 days ahead. Use one or the other.
max_attempts(n)5Claims before the job dies (1–100).

Claims, leases and fencing

A claim takes up to 100 claimable jobs of one scope — due pending jobs, and claimed jobs whose lease lapsed — lowest priority first, then group turns, then the job that waited longest. Each claim:

  • uses one of the job's attempts;
  • holds a lease (30 seconds by default, at most an hour) that the worker renews while it works;
  • carries a secret token that every renewal and report must present;
  • carries a fencing token, larger than every one issued before it in that queue and scope. Pass it to the downstream system so it can refuse a write from a worker whose lease lapsed and was taken over.

The worker then reports one of: complete (keep the job with a result), finish (delete it), fail (pending again after a delay, keeping its turn, or dead once attempts run out), kill (dead now) or release (hand it back without spending an attempt). A lapsed lease redelivers the job, so queues are at-least-once: make the work idempotent, or fence it.

Claims are tied to the database's history: after a restore to an earlier point, holders of old claims can no longer renew or report.

Who claims

Usually a native worker built with flower-worker, over the worker HTTP endpoints (/v1/queue/poll, /complete, …) with the server's worker token. Native workers may name any queue, but never enqueue: jobs come only from mutations. Guest mutations can claim and report too, through the typed handle's claim, complete, renew and friends, which is useful for work that stays inside the database. Goblin Pizza's pizza.deliver renews a delivery drone's lease inside the paying mutation, so a drone whose lease lapsed cannot collect payment.

Queries can watch a queue: stats and ready (on the typed handle, or Queue::stats and Queue::ready by name) return counts and whether a claim would succeed, from any context, and a query reading them is re-run when that changes — when a delayed job falls due or a lease lapses. The flower-worker crate uses this to sleep until there is work.

Timers

A mutation schedules a timer by a stable ID: at a due time, the leader runs a mutation of the same module (the handler) with the arguments you gave. The handler is the mutation's own static and the arguments its own argument struct, so a mistake is a compile error; the arguments are also checked against its contract when the timer is scheduled. Scheduling an existing ID replaces the timer, which makes debouncing trivial.

const TRIAL: Duration = Duration::from_secs(14 * 24 * 60 * 60);

/// Timer IDs are any text up to 128 bytes, without control characters.
fn trial_timer(account: &str) -> String {
    format!("trial:{account}")
}

#[mutation(http)]
pub fn start_trial(ctx: &mut MutationCtx<'_, '_>, account: String) -> Result<()> {
    Trials::set(ctx, &account, &Trial { active: true })?;
    // The handler is the mutation's descriptor and its arguments its own
    // argument struct, checked now. Scheduling an existing ID replaces
    // that timer.
    let args = EndTrialArgs {
        account: account.clone(),
    };
    Timers::after(ctx, &trial_timer(&account), TRIAL, &END_TRIAL, &args)
}

/// The timer's handler: an ordinary mutation of this module. Without
/// `http`, nothing outside the module can call it.
#[mutation]
pub fn end_trial(ctx: &mut MutationCtx<'_, '_>, account: String) -> Result<()> {
    Trials::set(ctx, &account, &Trial { active: false })
}

#[mutation(http)]
pub fn convert(ctx: &mut MutationCtx<'_, '_>, account: String) -> Result<bool> {
    Trials::delete(ctx, &account)?;
    Timers::cancel(ctx, &trial_timer(&account))
}
  • The handler is a mutation of the same module. It needs no http, and an internal handler should have none: then no client can call it, as the 404 UNKNOWN_METHOD for end_trial shows.
  • Timers::after(ctx, id, delay, &HANDLER, &args) takes a core::time::Duration; Timers::at an epoch-millisecond due time. Timers::schedule is the full form, over any mutation descriptor and raw arguments, with ScheduleOptions.
  • The due time means "not before". The leader fires due timers through the log on its maintenance tick (--timer-sweep-ms, one second by default) and as soon as a timer falls due, using the module's current code.
  • A handler that fails is retried, up to max_attempts (3 by default, at most 100, set through ScheduleOptions); after that the timer is dead. Operators inspect and revive timers with cargo flower timer, and guests with Timers::get and scan (from any context) and retry.
  • Timer IDs are any text of 1 to 128 bytes without control characters, so free-form identifiers work as they are: 
    $ cargo flower timer --db shop list
{"args":{"account":"ada"},"attempts":0,"due_ms":1794752193392,"handler":"end_trial","id":"trial:ada","max_attempts":3,"state":"pending"}
  • Timer firings have no caller and no principal; the authorization hook does not run for them.

Registering them

The queue is a component; the timer's handler is an ordinary mutation:

pub static APP: App = App::new(&[
    &MAIL,
    &Trials,
    &INVITE,
    &INVITATION_SENT,
    &START_TRIAL,
    &END_TRIAL,
    &CONVERT,
]);

Queues, timers or tasks?

UseWhen
A queueThe work happens outside Flower, may fail and be retried, and needs a worker process.
A timerA specific thing must happen inside Flower at or after a specific time: expire a trial, finish baking a pizza.
A maintenance taskPeriodic housekeeping whose need you can compute from the data: purge expired sessions, compact old rows.
