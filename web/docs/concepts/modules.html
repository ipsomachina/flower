Concepts

Modules and interfaces

Several modules can share a database and commit together, while each keeps its data private. A module exposes exactly what it exports; other modules reach it through contracts that deployment checks for compatibility.

Private by default

A module's collections, derived values and methods are invisible to other modules unless their declarations export them. Reading or calling something not exported fails with MODULE_PRIVATE. Exported collections are read-only to other modules (MODULE_READ_ONLY): changes always go through the owner's own mutations, so its checks, triggers and references always run.

Exports

An export is a flag on the declaration it concerns: export on #[collection], #[query], #[mutation] and #[derived], or callers("shop", ...) on a method to admit only the modules it names:

/// Without an interface, exports are flags on the declarations: other
/// modules may read this collection...
#[collection(name = "prices", key = String, value = u64, export)]
pub struct Prices;

/// ...and only `shop` and `reports` may call this query (`export`
/// alone would admit every module).
#[query(callers("shop", "reports"))]
pub fn price(ctx: &mut QueryCtx<'_, '_>, sku: String) -> Result<u64> {
    Ok(Prices::get(ctx, &sku)?.unwrap_or(0))
}

A method with a callers allowlist refuses every other module with MODULE_PRIVATE. Allowlists name actual module names, never slots. Raw descriptors say the same with .export() and .export_to(&["shop"]); an empty allowlist admits no module. Exports change nothing inside the module itself, and HTTP exposure is separate: http governs clients, export governs other modules.

Other modules read exported collections through typed handles pointed at the provider: Items::SOURCE.in_module("warehouse") or an index handle's in_module, and call exported methods with ctx.call, try_call, call_mutation and try_mutation (see Calling other modules).

Interface crates

Modules are separate Wasm artifacts that share no code at run time — only contracts. The tidy way to share a contract is an interface crate: a plain library both modules depend on, holding the types and a trait annotated with #[interface]:

#[derive(FlowerType, Clone, Debug, PartialEq)]
pub struct Item {
    pub name: String,
    pub stock: u64,
}

#[derive(FlowerError, Clone, Debug, PartialEq)]
pub enum StockError {
    #[flower(code = "UNKNOWN_ITEM")]
    Unknown,
    #[flower(code = "OUT_OF_STOCK")]
    OutOfStock(u64),
    #[flower(other)]
    Host(Failure),
}

/// The contract, versioned in its name: an incompatible change gets a
/// new interface rather than breaking deployed consumers.
#[interface(name = "inventory.v1", handle = InventoryApi)]
pub trait Inventory {
    #[query]
    fn item(ctx: &mut QueryCtx<'_, '_>, sku: String) -> flower_sdk::Result<Option<Item>>;

    #[mutation]
    fn reserve(
        ctx: &mut MutationCtx<'_, '_>,
        sku: String,
        quantity: u64,
    ) -> core::result::Result<u64, StockError>;
}

From that one trait the macro generates both sides:

  • For the provider, InventoryProvider<P>: implement the trait on any type P, then list InventoryProvider::<P>::COMPONENT among the app's components. It brings the interface's methods, exported to every module, and nothing else. They stay off HTTP unless you list COMPONENT.http() instead; to give them access rules, name them in the authorization component's methods table.
  • For consumers, the handle InventoryApi: one static, InventoryApi::import("$inventory"), is both the import component the app lists and the typed call handle, with methods (item, reserve) and savepoint variants (try_item, try_reserve) that decode the declared error type.

The provider:

#[collection(name = "items", key = String, value = Item)]
pub struct Items;

pub struct Warehouse;

impl Inventory for Warehouse {
    fn item(ctx: &mut QueryCtx<'_, '_>, sku: String) -> flower_sdk::Result<Option<Item>> {
        Items::get(ctx, &sku)
    }

    fn reserve(
        ctx: &mut MutationCtx<'_, '_>,
        sku: String,
        quantity: u64,
    ) -> core::result::Result<u64, StockError> {
        let mut item = Items::get(ctx, &sku)?.ok_or(StockError::Unknown)?;
        if item.stock < quantity {
            return Err(StockError::OutOfStock(item.stock));
        }
        item.stock -= quantity;
        Items::set(ctx, &sku, &item)?;
        Ok(item.stock)
    }
}

/// The provider component brings the interface's methods, exported to
/// every module. Add `.http()` to let callers reach them over HTTP too.
pub static PROVIDER_APP: App = App::new(&[&Items, &InventoryProvider::<Warehouse>::COMPONENT]);

A consumer:

/// Wherever this deployment's `inventory` binding points: the typed
/// call handle and the import declaring the contract it must meet.
static INVENTORY: InventoryApi = InventoryApi::import("$inventory");

#[mutation(http)]
pub fn checkout(ctx: &mut MutationCtx<'_, '_>, sku: String, quantity: u64) -> Result<String> {
    match INVENTORY.try_reserve(ctx, sku, quantity) {
        Ok(CallOutcome::Success(left)) => Ok(alloc::format!("reserved; {left} left")),
        Ok(CallOutcome::Failure(StockError::OutOfStock(left))) => {
            Ok(alloc::format!("only {left} left"))
        }
        Ok(CallOutcome::Failure(other)) => {
            Err(fail("CHECKOUT_FAILED", alloc::format!("{other:?}")))
        }
        Err(CallError::Host(failure)) => Err(failure),
    }
}

pub static CONSUMER_APP: App = App::new(&[&INVENTORY, &CHECKOUT]);

The repository's examples/typed-modules-contract, -provider and -consumer crates are a complete, deployable version of this pattern.

Slots and bindings

The consumer above imports "$inventory", a slot, rather than a concrete module name. Each deployment binds the slot to a module, so the same binary can run against different providers in different databases:

cargo flower deploy --db store --module warehouse --wasm provider.wasm --admin-token secret
cargo flower deploy --db store --module shop --wasm consumer.wasm --admin-token secret \
  --bind inventory=warehouse

Deploying without the binding is refused before anything is sent:

cargo-flower: invalid_module (preflight; nothing was sent): slot `$inventory` is not bound: deploy with --bind inventory=<module>

Bindings become part of the deployed manifest and of its content identity. Every imported slot must be bound and every binding used; module names never start with $. To point a consumer at another provider, deploy the same binary again with another binding. --bindings FILE takes the same map as a JSON object.

Compatibility checks

When you deploy a module, the server checks its imports against the providers deployed in the database, and checks every deployed importer against what the module is about to export. A provider must accept every argument the importer may send, and may only return results and declared errors the importer accepts; exported collections must agree on keys and fit the importer's row type. A change that would break a link is refused with 409 MODULE_CONFLICT, naming what would break. You can run the same check offline before deploying:

cargo flower plan --wasm consumer.wasm --module shop \
  --with warehouse=provider.wasm --bind inventory=warehouse

At run time the host still holds every answer to the provider's declared contract: a result or error outside it fails with MODULE_CONTRACT_VIOLATION, as the callee's failure.

Versioning Compatibility is structural, so a provider can widen what it accepts and narrow what it returns without breaking anyone. For a breaking change, publish a new interface (inventory.v2), serve both from the provider for a while, and move consumers over.

Removing a module

cargo flower modules --db D remove --module M removes a module's code, HTTP names, hooks and derived values through the log. Its records stay, unreachable, so deploying it again brings them back; add --purge to delete its data too, in the background, page by page. A module another module imports from cannot be removed (MODULE_CONFLICT). See Deployments.
