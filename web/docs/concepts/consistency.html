Concepts

Revisions and consistency

Each database has one revision that moves with every committed change. Each query declares how fresh its answer must be — linearizable, or replica-local with or without a bound — and every member serves it accordingly.

Revisions and positions

A revision is a per-database counter that moves each time a mutation, transaction step, timer firing, task run or queue operation commits a change to that database. It identifies a state of one database; revisions of different databases are unrelated. A few things do not move it: deployments, business failures (which only record their outcome) and caches the engine fills while reading.

A position is the index of the log entry a change committed in, in the log of the group that owns the database. Positions are what operators see in backups and Raft metrics; revisions are what applications usually care about.

Where you see them:

AnswerRevision information
POST /v1/mutaterevision and position, also on the mutation's own failures (HTTP 422).
POST /v1/transactionrevision, position, revisions (per database) and, across groups, positions (per group).
POST /v1/watchEvery event carries the revision its value was computed at.
POST /v1/queryNone. A query answer is exactly {"ok":true,"value":…}.

Optimistic concurrency

A mutation request may carry expected_revision. If the database has moved past it by the time the mutation commits, the call fails with stale_revision (HTTP 422, with the revision the database is at) and changes nothing:

{"ok":false,"revision":1,"position":10,"code":"stale_revision","message":"expected revision 0 but the database is at 1","duplicate":false}

The check is database-wide: any change to the database moves its revision. Learn a revision from a previous mutation answer or a watch event. Most applications do not need this — a mutation's reads are validated at commit anyway — but it is useful for "save only if nobody changed anything since I looked" flows across several requests.

Query consistency

Consistency is part of a query's declaration:

#[query(http)] // linearizable
fn balance(ctx: &mut QueryCtx<'_, '_>, account: String) -> Result<Option<u64>> { … }

#[query(http, max_staleness_ms = 2000)] // ReplicaLocalWithin(2_000)
fn leaderboard(ctx: &mut QueryCtx<'_, '_>) -> Result<Vec<Score>> { … }

#[query(http, consistency = replica_local)] // ReplicaLocal
fn catalog(ctx: &mut QueryCtx<'_, '_>) -> Result<Vec<Item>> { … }

To serve one callback under two consistencies, declare a twin: BALANCE.named("balance_nearby").consistency(Consistency::ReplicaLocalWithin(2_000)) (see Queries).

ConsistencyGuaranteeHow a member serves it
Linearizable (the default)Reflects every write that completed before the query began, whichever members served the write and the query.The leader answers under its read lease or after a quorum round; a follower asks the leader for the commit index, waits until it has applied it, then reads its own copy.
ReplicaLocalWithin(ms)At most ms milliseconds stale.From its own state while within the bound; otherwise it proves a fresh read first (and reports staleness 0), or answers 503 stale_replica if it cannot.
ReplicaLocalSome committed state, possibly far behind; never ahead of what is committed.Immediately, from its own state.

Replica-local answers carry an x-flower-staleness-ms header: the member's estimate in milliseconds, 0 when it proved a fresh read, or unknown. Linearizable answers never carry it.

A caller can tighten a replica-local query's bound with the x-flower-max-staleness-ms request header (or RequestOptions::max_staleness in the Rust client), but can never loosen it, and cannot make a linearizable query replica-local. x-flower-max-staleness-ms: 0 asks for a proven-fresh answer from a replica-local query.

Read-your-writes

Linearizable queries always see the caller's completed writes, on any member. Replica-local queries may not: a follower that has not yet applied your write answers from before it. Use replica-local queries for reads that can lag — dashboards, browsing, leaderboards — and keep checks that guard money or stock inside mutations, which always run on the leader against the latest state.

Pattern Goblin Pizza (examples/goblin-pizza) declares pizza.shop as a linearizable query and pizza.shop.local as its replica-local twin over the same callback. Clients browse with the local one and buy with mutations.

Leader leases and read leases

Proving a read linearizable normally takes a round trip to a quorum. Flower avoids most of them with a read lease: after a quorum round, the leader may answer linearizable reads on its own for a short time (by default 270 ms, nine tenths of the 300 ms leader lease), renewing the lease in the background. A leadership transfer or a membership change ends the lease.

The lease relies on member clocks advancing at roughly the same rate and never stopping while the process runs. A host that suspends a running member (to RAM, say) can make it serve one stale read when it wakes; set --raft-read-lease-ms 0 on such hosts to make every fresh read take a quorum round. The timing flags are described in Operating a cluster.

Routing and failover

Any member accepts any call. Queries run where they arrive, as declared. Writes, transactions and other leader-only requests are forwarded by a follower to the leader and the leader's answer is relayed verbatim; every answer names the leader's URL in x-flower-leader-url, so clients can go there directly next time (the Rust client does this with leader_routing(true)).

When a leader fails, a new one is elected in about half a second with the default timing. Writes sent to a follower meanwhile are held and forwarded when the new leader appears. A few answers mean the outcome of a write is unknown — the write may or may not have committed:

  • 503 leader_isolated: the leader lost its quorum for longer than its lease plus the election timeout (400 ms by default) and gave up the writes it held.
  • 503 forward_failed: a forward broke after the request may have reached the leader.
  • A timeout or a dropped connection.

Retry those with the same request ID, and the retry answers the original outcome if there was one. See Retries and receipts.
