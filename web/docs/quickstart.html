Get started

Quickstart

Build a to-do module in Rust, serve it on a one-node cluster, and call it over HTTP. Every command and output on this page was run against the current Flower code.

Prerequisites

  • Rust 1.96 or newer with the WebAssembly target: rustup target add wasm32-unknown-unknown.
  • A C compiler, for the zstd codec the server links. On Windows on ARM64, also install LLVM (winget install LLVM.LLVM) and put its bin directory on PATH before building: the TLS library's assembly needs clang.
  • A checkout of the Flower repository. The crates are not published to crates.io; your guest depends on flower-sdk by path.

1. Install cargo flower

From the root of the Flower checkout:

cargo install --path crates/cargo-flower

This installs the cargo-flower binary, which Cargo runs as cargo flower. The same binary builds guests, deploys them, calls them and serves cluster nodes. A release build takes a few minutes the first time: it compiles the whole server, including the Wasm compiler.

2. Write a module

Create a library crate next to your Flower checkout:

cargo new --lib tasks
cd tasks

A guest is a cdylib that depends on flower-sdk and nothing else. Building it as an rlib too lets tests and Rust clients link its types:

Replace src/lib.rs with the module. It declares a tasks collection indexed by whether a task is done, two mutations and one query, all three callable over HTTP:

A few things to notice:

  • #[derive(FlowerType)] gives Task a schema and a codec. The wire names are the Rust field names.
  • #[collection] turns the Tasks marker into the collection's typed handle — get, set and delete by key, and a typed BY_DONE index handle — and into the component the app lists. Keys are values of the declared key type: Tasks::get(ctx, &id) takes the String itself.
  • #[mutation] and #[query] keep the function and declare the operation: a static named after the function in upper case (ADD_TASK) and a public argument struct (AddTaskArgs) whose fields are the parameters after ctx. The JSON arguments object has those fields.
  • Nothing answers over HTTP unless its declaration says http. The method's name is its HTTP name; #[mutation(name = "tasks.add", http)] picks another.
  • App::new takes one flat list of components: collections, methods, and later queues, keys or an authorization hook. export!(APP) emits the Wasm exports the server calls.

3. Build it

cargo flower build
built tasks wasm=.flower/tasks.wasm manifest=.flower/tasks.manifest.json sha256=f3eca4e1f4e308ced6fd1684a06156c19a6664e6364c58cd8c168bd590d2fee8
collections=1 queries=1 mutations=2 derived=0 transactions=0 triggers=0 http=3

build compiles the crate for wasm32-unknown-unknown in release mode, then loads the result through the same Wasm backend the server uses and checks its imports, exports and manifest. Nothing is written unless that inspection passes. The manifest — collections, schemas, methods and the names callable over HTTP (aliases) — is embedded in the module; the .manifest.json copy is for you to read and diff.

4. Start a node

In a second terminal:

cargo flower serve --dir data --id 1 --bootstrap 1 --admin-token secret
listening raft=127.0.0.1:9000
listening http=127.0.0.1:8080
  • --dir is where the node keeps its data; --id is its member ID.
  • --bootstrap 1 founds a new one-member cluster on first start. It is ignored once the directory is initialized, so restarting with the same command is safe.
  • --admin-token enables the operator endpoints, deployment included. Without it every admin request is refused with 403.

The node serves HTTP/1.1 and HTTP/2 on port 8080 and Raft on port 9000, both on loopback. It logs at info; set RUST_LOG=warn for a quieter terminal. Check that it elected itself:

cargo flower status
id=1 state=Leader leader=Some(1) term=1 last_log=Some(2) last_applied=Some(2)

Client commands talk to http://127.0.0.1:8080 unless you pass --endpoint or set FLOWER_ENDPOINT.

5. Deploy

cargo flower deploy --db demo --module tasks --wasm .flower/tasks.wasm --admin-token secret
revision=0 position=3

This creates the database demo and deploys the artifact into it as the module tasks. The deployment went through the Raft log (position 3); it did not move the database's revision, which counts data changes. You could deploy the same file again as another module, or into another database.

6. Call it

Mutations go to POST /v1/mutate; the body names the database, module, method and arguments:

curl -s http://127.0.0.1:8080/v1/mutate -H 'content-type: application/json' \
  -d '{"db":"demo","module":"tasks","name":"add_task","args":{"id":"milk","title":"Buy milk"},"idempotency_key":"add-milk"}'
{"ok":true,"value":{"done":false,"title":"Buy milk"},"revision":1,"position":4,"duplicate":false}

The answer carries the method's return value, the database revision the write produced, and the log position it committed at. Send exactly the same request again:

{"ok":true,"value":{"done":false,"title":"Buy milk"},"revision":1,"position":4,"duplicate":true}

Because the request carried an idempotency_key, the server recognized the retry and answered the original outcome instead of running add_task again — note "duplicate":true and the unchanged revision. Without a key, the second call would run and fail with the module's own error:

HTTP/1.1 422 Unprocessable Entity

{"ok":false,"revision":1,"position":5,"code":"TASK_EXISTS","message":"a task with this ID already exists","duplicate":false}

A method's own failure answers 422, with "ok":false and your code and message. Nothing it wrote was kept and the revision did not move; the log entry at position 5 records only the failed outcome. See Retries and receipts for how long Flower remembers keys.

Add a second task the same way, with {"id":"bread","title":"Bake bread"}. Queries go to POST /v1/query:

curl -si http://127.0.0.1:8080/v1/query -H 'content-type: application/json' \
  -d '{"db":"demo","module":"tasks","name":"open_tasks","args":{}}'
HTTP/1.1 200 OK
content-type: application/json
x-flower-leader-url: http://127.0.0.1:8080
server-timing: cache;desc=miss, fence;dur=0.3, admission;dur=0.0, eval;dur=1.0, total;dur=1.5, node;desc=1, leader;desc=1
x-flower-group: root

{"ok":true,"value":[{"id":"milk","title":"Buy milk"},{"id":"bread","title":"Bake bread"}]}

A query answer carries only the value. Server-Timing breaks the request down into phases — here a result-cache miss, the fence that proved the read fresh, and the evaluation — and you can read it in your browser's network panel. See the HTTP reference.

The CLI can make the same calls. --mutation selects /v1/mutate:

cargo flower call --db demo --module tasks --name complete_task --args '{"id":"milk"}' --mutation
{"done":true,"title":"Buy milk"}
revision=3 position=7 duplicate=false

7. Watch a query

A watch keeps a query's result current over server-sent events. POST /v1/watch takes exactly the body of /v1/query:

curl -sN http://127.0.0.1:8080/v1/watch -H 'content-type: application/json' \
  -d '{"db":"demo","module":"tasks","name":"open_tasks","args":{}}'

Leave it running and, in another terminal, add a task and complete one. Each change that alters the query's result produces a new snapshot:

event: snapshot
data: {"revision":3,"id":1,"value":[{"id":"bread","title":"Bake bread"}]}

event: snapshot
data: {"revision":4,"id":3,"value":[{"id":"eggs","title":"Buy eggs"},{"id":"bread","title":"Bake bread"}]}

event: snapshot
data: {"revision":5,"id":4,"value":[{"id":"eggs","title":"Buy eggs"}]}

Add "deltas":true to the body to receive JSON Patch events instead, whenever a patch is smaller than the value:

event: patch
data: {"revision":4,"id":3,"base":2,"patch":[{"op":"add","path":"/0","value":{"id":"eggs","title":"Buy eggs"}}]}

The engine knows which index range open_tasks read, so writes that cannot change its result never wake the watch. See Watches.
