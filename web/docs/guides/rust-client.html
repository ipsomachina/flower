Calling Flower from Rust

flower-client is an async HTTP client for Flower: plain and typed calls, request IDs and retries, deadlines and cancellation, reconnecting watches, transactions, queue and admin calls.

Setup

Add the crate by path from your Flower checkout, with Tokio and serde:

The guest crate builds natively as an rlib (the quickstart's crate-type = ["cdylib", "rlib"]), so the client can use its declarations for typed calls. The default remote client uses reqwest with rustls and does not link the engine or Wasmtime. Enable the replica feature for local sync-down and offline intent queues. A shared interface crate supplies native contract descriptors without linking the provider implementation. On Windows on ARM64, building it needs LLVM's clang on PATH, as for the server.

Connecting

pub fn connect(token: &str) -> Result<FlowerClient, FlowerError> {
    FlowerClient::builder("http://127.0.0.1:8080")
        .credentials(Credentials::token(token))
        // Retry transient failures, with backoff, and ride out overload.
        .retry(Retry::Default)
        // Send writes straight to the leader each reply names.
        .leader_routing(true)
        // Each attempt's timeout (the default is 20 s).
        .timeout(Duration::from_secs(10))
        .build()
}
  • The client talks to one base URL. Any member works: followers forward writes. With leader_routing(true), the client remembers the leader each answer names (x-flower-leader-url, per database) and sends writes there directly, falling back to the base URL when the leader stops answering.
  • Credentials::token sends Authorization: Bearer …. A token that is not one of the server's own tokens reaches the module's authorization hook as {"bearer": token}; the server's admin token makes the client a trusted gateway. Credentials::from_fn consults a closure on every attempt, for tokens that refresh.
  • Over http:// the client speaks HTTP/2 without TLS (h2c) and multiplexes every call over one connection; TransportOptions::new().protocol(Protocol::Http1) switches to HTTP/1.1. Over https:// it negotiates HTTP/2 by ALPN and trusts the platform's roots plus any added with .ca_file(path).
  • Retries are off by default. .retry(Retry::Default) turns them on for every call; individual calls can override it. See Errors and retries.
  • FlowerClient is cheap to clone; clones share connections.

Queries and mutations

query and mutate take any serde-serializable arguments and deserialize the result; query_value and mutate_value work with serde_json::Value. Every call names the database, the module and the method's HTTP name, and the caller picks query or mutation. These calls need nothing from the guest, so they suit scripts and other teams' services; with the guest crate at hand, prefer typed calls:

#[derive(Serialize)]
struct AddTask<'a> {
    id: &'a str,
    title: &'a str,
}

#[derive(Deserialize, Debug)]
pub struct Task {
    pub title: String,
    pub done: bool,
}

#[derive(Deserialize, Debug)]
pub struct OpenTask {
    pub id: String,
    pub title: String,
}

pub async fn add_and_list(client: &FlowerClient) -> Result<Vec<OpenTask>, FlowerError> {
    // A request ID chosen per intent: retrying it can never add twice.
    let options = MutationOptions::new().request_id("add-milk");
    let args = AddTask {
        id: "milk",
        title: "Buy milk",
    };
    let added: MutationResult<Task> = client
        .mutate("demo", "tasks", "add_task", &args, &options)
        .await?;
    println!(
        "{:?} at revision {} (duplicate: {})",
        added.value, added.revision, added.duplicate
    );

    let open: QueryResult<Vec<OpenTask>> = client
        .query(
            "demo",
            "tasks",
            "open_tasks",
            &json!({}),
            &RequestOptions::new(),
        )
        .await?;
    Ok(open.value)
}

A MutationResult carries the request ID, optional read token, method's value, the revision and position it committed at, and duplicate — true when a stored receipt answered a retry. A QueryResult carries the value and, for replica-local queries, the reported staleness; RequestOptions::max_staleness tightens a replica-local query's bound.

Request IDs Each mutate call fixes one request ID before its first attempt — yours, or a fresh UUID — so the client's own retries are always safe. To retry safely across calls or process restarts, choose the ID yourself from the intent, persist it, and pass it with request_id. See Retries and receipts.

Scoped handles and persisted commands

Bind the database and module once with client.database("demo").module("tasks"). Query descriptors can be queried or watched; mutation descriptors can be prepared as serializable commands. Shared #[interface] contracts emit native descriptors on their handles and public argument types, without requiring the provider implementation.

Add client = TasksClient to generate named query methods and prepare_* mutation methods. Bind the facade with TasksApi::client(module); its public remote backend executes persisted commands. The shared contract still needs only the SDK, including when compiled for Wasm.

Scoped query builders take QueryOptions; prepared commands and typed transactions take CommandOptions. Both carry delivery settings, while only queries expose staleness and causal bounds. Convert legacy query options with into(), and command options with CommandOptions::try_from(legacy), which refuses read constraints instead of discarding them.

#[flower_sdk::interface(name = "tasks.v1", handle = TasksApi, client = TasksClient)]
pub trait TasksContract {
    #[query]
    fn get_task(
        ctx: &mut flower_sdk::QueryCtx<'_, '_>,
        id: String,
    ) -> flower_sdk::Result<Option<tasks::Task>>;
    #[mutation]
    fn add_task(
        ctx: &mut flower_sdk::MutationCtx<'_, '_>,
        id: String,
        title: String,
    ) -> flower_sdk::Result<tasks::Task>;
}

pub async fn prepare_with_generated_client(
    client: &FlowerClient,
) -> Result<flower_client::PreparedCommand<tasks::Task>, FlowerError> {
    let tasks = TasksApi::client(client.database("demo").module("tasks"));
    let current = tasks
        .get_task(&TasksContractGetTaskArgs { id: "milk".into() })
        .await
        .map_err(|error| error.source().clone())?;
    println!("current value: {:?}", current.value);
    // Persist the returned command before tasks.remote.execute(...).
    tasks
        .prepare_add_task(&TasksContractAddTaskArgs {
            id: "milk".into(),
            title: "Buy milk".into(),
        })
        .await
}
/// Prepare once; durably store the serialized command before its first execution.
pub async fn prepare_task(
    client: &FlowerClient,
    id: String,
    title: String,
) -> Result<flower_client::PreparedCommand<tasks::Task>, FlowerError> {
    let operation = ADD_TASK
        .as_mutation()
        .map_err(|failure| FlowerError::Decode(failure.message))?;
    client
        .database("demo")
        .module("tasks")
        .prepare(&operation, &AddTaskArgs { id, title })
        .await
}

/// A recovered command retains its identity and returns all commit metadata.
pub async fn execute_task(
    client: &FlowerClient,
    command: &flower_client::PreparedCommand<tasks::Task>,
) -> Result<
    flower_client::CommandResult<tasks::Task>,
    flower_client::CommandError<flower_sdk::Failure>,
> {
    client
        .database("demo")
        .module("tasks")
        .execute(command, &CommandOptions::retrying())
        .await
}

Durably store the serialized command before execution and recover that exact command after a crash. Preparation requires initialized retry retention and an established history incarnation. prepare_with_identity supports a previously stored identity offline. CommandResult keeps typed revision and log position counters, the request ID, replay indicator and an optional read token. CommandError keeps the request ID and the underlying failure's execution certainty. A refused redelivery does not resolve a previous delivery whose outcome was unknown.

scope.query(&QUERY, &args).at_least(token).await requires the query to include committed state from that token. Tokens bind database, group and history; command.if_unchanged(&token) checks a database revision precondition. A sync position is a different counter. Missing freshness metadata means unknown staleness.

client.protocol(options).await?.require(&["read_tokens"]) checks optional capabilities. Custom transports must preserve headers or explicitly refuse the request. Use TransportOptions::direct() for Flower directly and proxy() for HTTP/1.1 through a plain-HTTP proxy.

Generated workflow builders

Generated mutation methods also return a builder: tasks.add_task(&args).prepare().await prepares an unsent command, while .enqueue(&outbox).await persists it before returning a handle. Deliver the stored command with handle.execute(&options).await. Existing prepare_* methods remain available. Custom backends opt in through the SDK's RemoteCommands trait.

pub async fn enqueue_with_generated_client(
    client: &FlowerClient,
    outbox: &flower_client::CommandOutbox,
    args: &TasksContractAddTaskArgs,
) -> Result<
    flower_client::CommandHandle<tasks::Task>,
    flower_client::OutboxError<flower_sdk::Failure>,
> {
    let tasks = TasksApi::client(client.database("demo").module("tasks"));
    // Returns only after persistence. Execute this handle to deliver the mutation.
    tasks.add_task(args).enqueue(outbox).await
}

pub fn subscribe_with_generated_client(
    client: &FlowerClient,
    id: String,
) -> Result<
    flower_client::DeclaredSubscription<Option<tasks::Task>, flower_sdk::Failure>,
    RemoteError<flower_sdk::Failure>,
> {
    let tasks = TasksApi::client(client.database("demo").module("tasks"));
    tasks.get_task(&TasksContractGetTaskArgs { id }).subscribe()
}

A query builder supports .watch().await for a single connection and .subscribe() for reconnecting snapshots. Credentials, connect timeout and cancellation carry into the stream. Query causal bounds, staleness, whole-call deadlines and retry overrides are rejected before opening a stream; use the explicit subscription API for reconnect options. Session-bound streams remain unsupported.

RemoteError, CommandError and TransactionError expose declared(), problem() and execution(). Their underlying causes remain available; unknown execution is not evidence of rejection.

Typed calls and declared errors

Every #[query] and #[mutation] declares a static descriptor, an Op<Args, T, E>, and a public argument struct. With the guest crate as a dependency, client.call(db, module, &OP, &OpArgs { .. }) takes the method's name and kind from the descriptor, encodes the arguments with the SDK's own codec, decodes the result as the method's return type and a failure as the method's error type. A renamed method, a changed argument or a changed result type is then a compile error in the client, not a 404 or a decode failure in production:

use doc_snippets::methods::{TRANSFER, TransferArgs, TransferError};
use tasks::{ADD_TASK, AddTaskArgs, OPEN_TASKS, OpenTasksArgs};

/// The guest crate is a dependency (built as an `rlib` too): each
/// `#[query]` or `#[mutation]` static carries its name, its kind, its
/// argument struct, its result type and its declared errors.
pub async fn add_milk(client: &FlowerClient) -> Result<Vec<tasks::OpenTask>, FlowerError> {
    let args = AddTaskArgs {
        id: "milk".to_string(),
        title: "Buy milk".to_string(),
    };
    client
        .call("demo", "tasks", &ADD_TASK, &args)
        .await
        .map_err(|error| error.source().clone())?;
    client
        .call("demo", "tasks", &OPEN_TASKS, &OpenTasksArgs {})
        .await
        .map_err(|error| error.source().clone())
}

/// A failure the method declares comes back typed.
pub async fn pay(client: &FlowerClient, from: &str, amount: u64) -> Result<String, FlowerError> {
    let args = TransferArgs {
        from: from.to_string(),
        to: "merchant".to_string(),
        amount,
    };
    match client.call("bank", "bank", &TRANSFER, &args).await {
        Ok(left) => Ok(format!("paid; {left} left")),
        Err(RemoteError::Declared { error, source }) => match *error {
            TransferError::InsufficientFunds(balance) => {
                Ok(format!("declined: balance is {balance}"))
            }
            _ => Err(*source),
        },
        Err(other) => Err(other.source().clone()),
    }
}

/// `call` sends a mutation under a fresh request ID; `call_with` takes
/// options. Here the request ID names the payment, so sending it again
/// answers the first attempt's outcome instead of paying twice.
pub async fn pay_once(
    client: &FlowerClient,
    from: &str,
    amount: u64,
) -> Result<u64, RemoteError<TransferError>> {
    let args = TransferArgs {
        from: from.to_string(),
        to: "merchant".to_string(),
        amount,
    };
    let options = MutationOptions::retrying().request_id(format!("pay:{from}:{amount}"));
    client
        .call_with("bank", "bank", &TRANSFER, &args, &options)
        .await
}
  • call returns Result<T, RemoteError<E>>. A 422 failure the method's error type accepts comes back as RemoteError::Declared { error, source }, both boxed so the error stays small; anything else — transport, authorization, overload, a code the type does not declare — as RemoteError::Other. source() gives the underlying FlowerError either way. An error type with a #[flower(other)] catch-all accepts every code, so every 422 is Declared.
  • call uses default options: a query reads with the consistency it declares, and a mutation runs under a fresh request ID with the client's retry policy. To choose the request ID, an expected revision, a deadline or credentials, use call_with and MutationOptions, as pay_once does; a query takes the options' base (deadline, retries, staleness, credentials). For the whole answer — a mutation's revision, position and duplicate flag — use typed_mutate (below).
  • Without the guest crate — another team's module, say — typed_query and typed_mutate take any FlowerType arguments and result by name, and RemoteTarget::new(module, name) bundles a module and name for the *_at variants. For modules built separately, an interface crate gives both sides the same types.

Deadlines and cancellation

pub async fn open_tasks_soon(
    client: &FlowerClient,
    cancel: CancellationToken,
) -> Result<serde_json::Value, FlowerError> {
    let options = RequestOptions::retrying()
        // No attempt starts after this, and each is cut to what is left;
        // the server sheds work queued past it (x-flower-timeout-ms).
        .deadline(Instant::now() + Duration::from_secs(2))
        .cancel(cancel);
    let open = client
        .query_value("demo", "tasks", "open_tasks", &json!({}), &options)
        .await?;
    Ok(open.value)
}

Every attempt tells the server its remaining budget in x-flower-timeout-ms, so a request still waiting for admission when its caller has given up is dropped rather than run. A cancelled or timed-out mutation may still have committed: retry it with the same request ID.

Durable command storage and recovery

CommandOutbox verifies the complete contract and persists a command before allowing delivery. Its pluggable CommandStore supports atomic insert and compare-and-swap generations. FileCommandStore uses a checksummed, synced journal with OS file locking; it repairs a torn final entry and refuses complete-entry corruption. It replays the journal per operation and limits entries to 16 MiB. Use a database backend for larger histories; MemoryCommandStore is an ephemeral test backend.

pub async fn persist_task(
    client: &FlowerClient,
    journal: &std::path::Path,
    args: &TasksContractAddTaskArgs,
) -> Result<flower_client::CommandHandle<tasks::Task>, Box<dyn std::error::Error>> {
    let outbox = flower_client::CommandOutbox::new(Arc::new(
        flower_client::FileCommandStore::open(journal)?,
    ));
    let module = client.database("demo").module("tasks");
    let command = module.prepare(&TasksApi::ADD_TASK, args).await?;
    // No mutation has been sent. The returned handle owns the durable workflow.
    Ok(outbox
        .enqueue(&module, &TasksApi::ADD_TASK, &command)
        .await?)
}

pub async fn recover_task(
    client: &FlowerClient,
    journal: &std::path::Path,
    request_id: &str,
) -> Result<flower_client::CommandHandle<tasks::Task>, Box<dyn std::error::Error>> {
    let outbox = flower_client::CommandOutbox::new(Arc::new(
        flower_client::FileCommandStore::open(journal)?,
    ));
    let module = client.database("demo").module("tasks");
    // Checks the current complete contract; keeps the original request ID.
    Ok(outbox
        .resume(&module, &TasksApi::ADD_TASK, request_id)
        .await?)
}

Call handle.execute(&CommandOptions::retrying()).await to submit saved work. status() exposes Pending, Sending, Succeeded, Rejected, Unknown and Unresolved; updates() coalesces local lifecycle snapshots. An abandoned Sending state is uncertain. Explicit retry_uncertain replays the identical ID. Unresolved history or retention requires resolve with evidence of a decided business outcome. A later cancellation does not erase earlier uncertainty.

Command format 2 carries structural argument, result and declared-error fingerprints. Recovery checks all three schemas, retaining the original scope, ID and revision precondition. Pre-fingerprint snapshots require explicit migration or reconciliation. Fingerprints describe wire contracts, not unchanged business semantics. Credentials and delivery settings are supplied when executing, not persisted with commands.

Causal sessions

client.causal_session() opts into a shared unary causal context. Modules and generated clients retain tokens per database and automatically bound later reads by earlier observations. Clones share state. Operations within a database serialize; different databases remain independent. Deadlines and cancellation cover lock waits too. Missing token support or history mismatch causes an error instead of a weaker read.

pub async fn causal_roundtrip(
    client: &FlowerClient,
    args: &TasksContractAddTaskArgs,
) -> Result<QueryResult<Option<tasks::Task>>, Box<dyn std::error::Error>> {
    let session = client.causal_session();
    let tasks = TasksApi::client(session.database("demo").module("tasks"));
    let command = tasks.prepare_add_task(args).await?;
    tasks
        .remote
        .execute(&command, &CommandOptions::retrying())
        .await?;
    // The session automatically bounds this query by the committed write token.
    Ok(tasks
        .get_task(&TasksContractGetTaskArgs {
            id: args.id.clone(),
        })
        .options(
            flower_client::QueryOptions::new().deadline(Instant::now() + Duration::from_secs(5)),
        )
        .await?)
}

observe(token) imports a commit or watch token; token(db) exports current state. Proved reads and scoped writes can carry history across a move. reset(db) deliberately starts a new context after reconciliation. Tokens stay in memory unless the application persists them. Session-bound watches are refused; use a separate subscription and explicitly observe its tokens.

Protocol compatibility and custom transports

Typed requirements produce structured reports with missing capabilities, unknown extensions and peer/client versions. inspect_protocol inspects newer peers without accepting their format; a wider requested version range never enables an unimplemented protocol.

pub async fn require_causal_peer(
    client: &FlowerClient,
) -> Result<flower_client::protocol::ProtocolInfo, flower_client::protocol::NegotiationError> {
    use flower_client::protocol::{Capability, ProtocolRequirements};
    client
        .negotiate(
            &ProtocolRequirements::requiring([Capability::ReadTokens, Capability::ScopedCommands]),
            &RequestOptions::new(),
        )
        .await
}

Enable conformance to check a transport against the reusable HTTP/1.1 and h2c loopback harness. It verifies credentials, bytes, deadlines, causal headers, response metadata, retry hints, incremental streaming and response release on drop. This server dependency is absent from the default client.

#[tokio::test]
async fn transport_passes_the_probe_suite() -> Result<(), Box<dyn std::error::Error>> {
    use flower_client::{HttpTransport, TransportOptions, testing::conformance::ProbeServer};
    let server = ProbeServer::start().await?;
    let transport = HttpTransport::with_options(server.base_url(), TransportOptions::direct())?;
    // Substitute your own Transport here; the same checks apply.
    server.check(&transport).await.assert_passed();
    server.shutdown().await;
    Ok(())
}

Watches

Scoped subscriptions accept query descriptors and retain history identity, reset markers and read tokens. Monotonic suppression restarts when history changes or cannot be proved after reconnect. Terminal errors end the stream; transient errors reconnect with the retry hint. WatchOptions::cancel releases the connection and into_stream() adapts typed watches and subscriptions to futures streams.

Scoped watches and subscriptions also preserve the query's declared error type: both opening and terminal failures return RemoteError<E>. Inspect error.declared() for a domain failure and error.source() for the original structured failure. Authorization and host failures remain separate. The existing dynamic typed_watch and typed_subscribe APIs remain available.

Terminal SSE failures now retain the full FlowerError::Http problem, including application failures. Existing code matching Business on terminal events should inspect code() or problem(). Opening failures keep their unary representation.

A watch is a POST /v1/watch carrying the same body as a query, credentials included. subscribe opens one that reconnects by itself — with backoff after errors, at once after a clean end, and after 45 seconds without any bytes — and yields Update { revision, value, reset }. wait_until waits for a query's result to satisfy a predicate:

pub async fn follow_open_tasks(client: &FlowerClient) -> Result<(), FlowerError> {
    let mut subscription = client.subscribe::<Vec<OpenTask>>(
        "demo",
        "tasks",
        "open_tasks",
        &json!({}),
        &SubscribeOptions::default(),
    );
    while let Some(update) = subscription.next().await {
        let update = update?;
        // `reset` marks the first value after (re)connecting.
        println!(
            "revision {}: {} open{}",
            update.revision,
            update.value.len(),
            if update.reset {
                " (fresh snapshot)"
            } else {
                ""
            }
        );
    }
    Ok(())
}

pub async fn until_all_done(client: &FlowerClient) -> Result<u64, FlowerError> {
    let done = client
        .wait_until(
            "demo",
            "tasks",
            "open_tasks",
            &json!({}),
            |open: &Vec<OpenTask>| open.is_empty(),
            &SubscribeOptions::default(),
        )
        .await?;
    Ok(done.revision)
}
  • The client asks for deltas and applies them; you always receive whole values. A patch that does not apply makes it reconnect for a fresh snapshot.
  • After a reconnect, the first update has reset: true. Changes in between may have been coalesced: a watch is the current value, not an event log.
  • SubscribeOptions sets the reconnect retry policy, max_reconnects, the stall_timeout, and monotonic to drop updates older than one already seen.
  • watch, watch_deltas and typed_watch are single connections without reconnects; typed_subscribe is subscribe with FlowerType codecs.
  • A subscription that the server refuses for good — the method is gone or no longer exposed, the caller is no longer authorized — ends with that error.

Transactions

TypedTransaction::new().step(db, module, &mutation, &args)? builds a typed result tuple. Persist the serialized batch before executing; redelivery reuses its request ID. Each database appears once. Compose multiple same-database actions inside a guest mutation. Failures retain the failing step and database, with the callee's details under details.cause.

The builder also retains a tuple of declared error types. A failure's declared() exposes StepError::Step0(error) through Step7(error), using the same zero-based index as error.step. When restoring a batch, specify both tuples, such as TypedTransaction<(Invoice, Task), (BillingError, TaskError)>. The legacy one-parameter form keeps dynamic errors.

pub async fn archive(client: &FlowerClient, id: &str) -> Result<TransactionResult, FlowerError> {
    let steps = vec![
        TransactionStep {
            db: "demo".to_string(),
            module: "tasks".to_string(),
            method: "complete_task".to_string(),
            args: json!({"id": id}),
        },
        TransactionStep {
            db: "archive".to_string(),
            module: "tasks".to_string(),
            method: "add_task".to_string(),
            args: json!({"id": id, "title": "archived"}),
        },
    ];
    let options = TransactionOptions {
        request_id: Some(format!("archive:{id}")),
        ..TransactionOptions::new()
    };
    client.transaction(&steps, &options).await
}

See Transactions and partitions for the guarantees.

Restoring typed transactions

Typed transaction snapshots use local format 2 with per-step argument, result and declared-error fingerprints. Build a current typed template and call template.restore(saved): it checks participant scopes, contracts and saved argument decoding while retaining the saved request ID and arguments.

pub fn restore_archive_batch(
    saved: &[u8],
) -> Result<flower_client::TypedTransaction<(tasks::Task,), (flower_sdk::Failure,)>, FlowerError> {
    // A freshly built template supplies the current operation and argument decoder.
    // Its placeholder arguments and fresh ID do not replace the saved work.
    let template = flower_client::TypedTransaction::new().step(
        "archive",
        "tasks",
        &TasksApi::ADD_TASK,
        &TasksContractAddTaskArgs {
            id: String::new(),
            title: String::new(),
        },
    )?;
    template.restore(saved)
}

Execution also checks result/error fingerprints. Direct deserialization cannot check the original argument contract against current operation descriptors; use template restoration for recovery. Format-one snapshots require reconciliation or explicit migration using the original contract. Never prepare a new identity to recover an uncertain transaction. These local format checks do not change the server's transaction receipt retention or provide cross-group recovery parity with the command outbox.

Queues, timers and admin calls

The same client speaks the worker protocol — claim_queue, heartbeat_queue, report_queue, complete_queue_with, queue_readiness, get_queue_job and more — though you will usually let flower-worker drive it. Jobs are only ever enqueued by guest mutations. With the admin token it also deploys and stages modules, changes membership, lists and inspects timers, reads metrics and drives backups; these are the calls cargo flower itself makes.

Offline replicas

For devices, the client includes a sync-down replica (SyncClient) that follows a database's log into a local engine and serves reads offline, and an intent queue (IntentQueue) that stores mutations made offline and submits them, in order and under stable request IDs, when the device reconnects. These need the server's sync token.
