Guides

Deployments

A deployment replaces a module's code through the Raft log, atomically on every member. Build and plan offline, deploy in one call, or stage a large change and activate it when its indexes and derived values are ready.

Build

cargo flower build                       # the one cdylib in the workspace
cargo flower build --package tasks       # or name it
cargo flower build --features auth --out-dir dist

build compiles the package for wasm32-unknown-unknown (release profile by default), loads the module through the server's own Wasm backend, checks its imports and initialization, and reads the manifest it declares. Only then does it write <package>.wasm and <package>.manifest.json to .flower/ (or --out-dir) and print the artifact's SHA-256. The manifest — collections, schemas, definitions, HTTP names, access, exports, imports, queues, keys — is generated from the module's declarations and embedded in the Wasm; the JSON copy is for reading, diffing and review.

Plan

plan checks a deployment offline, without a cluster, and exits non-zero when it would break something. It prints what the module declares and the content identity the deployment will have, which covers the code and its bindings (it is not the file's SHA-256):

cargo flower plan --wasm .flower/tasks.wasm --current deployed.manifest.json
collections=1 queries=1 mutations=2 derived=0 transactions=0 triggers=0 http=3
bindings: none
identity=f009ff3a4a23231886633bc7afd20700d1d00cf253c0cba80b0dff5f4047a884
compatible=true
  • --current takes the deployed manifest (or the deployed Wasm) and diffs the contracts: removed collections or definitions, changed key types and changed kinds are incompatible.
  • --with MODULE=FILE (repeatable) adds the database's other modules, so the cross-module link check runs offline; --module names the module being deployed.
  • --bind SLOT=MODULE / --bindings FILE bind import slots; bindings change the content identity, which plan prints.
  • cargo flower contract inspect --manifest M prints a manifest; contract diff --from A --to B diffs two, marking incompatible lines with ! (it always exits 0: use plan to gate).

The server re-validates everything on deploy; plan only tells you earlier.

Deploy

export FLOWER_ENDPOINT=https://flower.internal:8080   # every command's default server
export FLOWER_ADMIN_TOKEN=…                          # from your secret store
cargo flower deploy --db shop --module shop --wasm .flower/shop.wasm --bind inventory=warehouse

The CLI runs the same preflight as plan and sends nothing if it fails. The leader then validates the module by building its runtime, checks links with the database's other modules (409 MODULE_CONFLICT), builds any new indexes over existing rows, and proposes the activation as one log entry. Every member switches at the same position. Deploying identical content again is a no-op, so retrying a deploy is safe. Two deploys of the same module at once: the second gets 409 deployment_in_progress. Bodies are limited to 64 MiB (--deploy-max-bytes).

What happens to traffic

  • Queries read either the old code with the old data or the new code with the new data, never a mix.
  • Mutations prepared under the old code but not yet committed are prepared again under the new code, transparently.
  • Derived values computed by the old code are re-evaluated on their next read (pinned ones eagerly); aggregates with an unchanged VERSION keep their groups.
  • Watches re-evaluate; a watch whose method the new code removed, or no longer declares http, ends with UNKNOWN_METHOD.
  • Timers fire with whatever code is current when they come due.

Changing collections and indexes

  • Adding collections, indexes and methods, or exposing a method over HTTP, is always fine. New indexes are built over existing rows before activation.
  • Changing a collection's value schema is accepted: existing rows stay as they are and stay readable, and new writes validate against the new schema. Migrating old rows is application work — a maintenance task that rewrites a page at a time is a good fit. Make new fields #[flower(default)] so old rows still decode.
  • An index's fields are fixed by its name. To index different fields, add an index under a new name and stop using the old one. (plan does not catch a changed index; the server refuses it.)
  • Removing collections or indexes retires them; the leader deletes their entries lazily in the background (cargo flower deployment … collect forces it).

Staged deployments

When the new code needs large indexes built or many derived values recomputed, stage it first. The old code keeps serving, writes go to both old and new indexes while the staging builds, and you activate when it is ready:

D="cargo flower deployment --db shop --module shop"
$D stage --wasm .flower/shop.wasm --manifest .flower/shop.manifest.json
$D advance --max-records 4096       # repeat until ready=true
$D status
$D activate                         # or: $D cancel
$D collect                          # later: delete what the old code left behind

stage, advance and status print the staging's progress; activate prints the revision and log position it switched at, after which status reports none:

ready=true position=0/0 retired=0 identity=9a849945…5840dc7f1 scanned=0 graph=0/0 rebuilt=0
revision=11 position=42
staging=none
  • stage validates the module like a deploy (it requires --manifest, and skips the CLI's local preflight).
  • advance builds a bounded page of index backfill (up to 65,536 records), then rebuilds derived roots under the new code (up to 1,024 a step). Each step is a log entry, so a new leader continues where the old one stopped.
  • activate re-checks links and switches atomically; it is refused until the staging is ready.
  • A one-call deploy of the same module replaces any open staging.

The admin dashboard (/admin) shows open stagings with buttons to advance, activate and cancel.

Bindings

A module that imports a slot ($inventory) must be deployed with a binding for it: --bind inventory=warehouse. Bindings are part of the deployed manifest and its identity; to rebind, redeploy the same artifact with another binding. See Slots and bindings.

Removing a module

cargo flower modules --db shop                                 # list
cargo flower modules --db shop remove --module legacy
cargo flower modules --db shop remove --module legacy --purge

Removal takes away the module's code, HTTP names, hooks and derived values through the log. Its records, indexes, queues and timers stay, unreachable — its due timers are held rather than spending their attempts — and come back if you deploy the module again. A module that another module imports from cannot be removed.

--purge deletes the data too, in the background, a page at a time: records and indexes, timers, maintenance-task state, and the queues the module declared that no other module declares, with their jobs. Until the purge ends, modules lists the module as purging, the module cannot be deployed again, no module declaring one of those queues can be deployed, and every operation on them — a guest's or a worker's — fails queue_purging.

From CI

A typical pipeline builds with --locked, runs plan --current against the manifest stored from the last release (failing the job on exit 1), deploys with FLOWER_ENDPOINT and FLOWER_ADMIN_TOKEN from the CI secret store, and stores the new manifest for next time. cargo flower modules shows each module's deployed identity, which matches the identity plan printed.

Module code, not Flower itself Deploying a module never restarts anything. Upgrading the Flower binary is a different operation, with its own rule: a member refuses to open files written under another compatibility contract. See Upgrading Flower.
