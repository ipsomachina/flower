Worker queues

flower-worker runs queue workers in your own Rust processes: it claims jobs, runs your handler, renews leases while it works, reports outcomes, adapts its concurrency to load, and drains cleanly when told to stop.

Jobs come from guest mutations, into queues their modules declare (see Queues and timers). This guide is about the other end. A native worker may name any queue of the database; it claims, renews and reports, but never enqueues.

Setup

Queue endpoints need the server's worker token (serve --worker-token / FLOWER_WORKER_TOKEN) or the admin token. Give workers the worker token: it can claim and report jobs and nothing else.

A worker

The handler gets a Claim — payload, attempts (this claim included), the fence token, the job's scope, priority, name and group — and returns:

Handler returnsReportEffect
Ok(())completeThe job is done and deleted.
Err(WorkError::Retry(Some(delay)))failPending again after delay, or dead once its attempts are spent.
Err(WorkError::Retry(None))failAs above, after the default backoff: 2 s after the first attempt, doubling, capped at 60 s (.retry(base, max)).
Err(WorkError::Terminal(reason))killDead now, whatever attempts remain. The reason stays in your process.
a panicfailAs Retry(None).

run_queue_worker returns a WorkerSummary counting completed, failed, killed, lost (lease lapsed or report refused) and drained jobs. Jobs completed by the worker are deleted; to keep a result with a job, report it yourself with client.complete_queue_with(…), or let a guest mutation complete the claim.

At least once A job whose lease lapses — the worker crashed, stalled or lost the network — is delivered again. Make handlers idempotent, or pass claim.fence to the downstream system and have it refuse writes carrying an older fence than one it has seen.

Leases

Each claim holds a lease (.lease(…), 30 seconds by default, at most an hour). The worker renews it every third of the lease while your handler runs. If a renewal is refused — the job was settled or taken over elsewhere — or none lands before the lease would end, the worker drops your handler's future and counts the job lost; it will be delivered again. Choose a lease comfortably longer than a renewal round trip, not longer than the time you are willing to wait for a crashed worker's jobs to come back.

Concurrency and backpressure

  • .concurrency(n) runs at most n handlers (4 by default).
  • .adaptive(min, initial, max) adjusts the limit: it grows while work keeps coming and the process is healthy, and cuts back when the process is busy (Tokio runtime saturation, memory on Linux) or Flower sheds load. Supply your own load signal with .health(…), and observe changes with .on_event(…).
  • Whenever the server refuses work for load (503 overloaded), the worker pauses claiming for a second and halves an adaptive limit.
  • The worker claims only what it can start now. Once claims come back full, up to .claimers(n) (4) claims run in parallel; a short claim falls back to one per .poll_interval(…) (1 s).

Lines and chained claims

Polling an empty queue wastes requests and adds latency. Two options remove most of it:

  • .wait(d) joins the scope's line. A claim that comes back short keeps the worker's place; the worker then reads readiness (a cheap query that wakes when work arrives) instead of claiming, and the first worker in line gets new work to itself for the queue's turn (one second by default; the declaring module sets it with TypedQueue::new("mail").turn_ms(..)). One process wakes per job instead of all of them. Stopping gives the place up.
  • .chain() makes every report also claim the next jobs, in the same commit: one round trip per job instead of two.

Idle jobs and throttling

run_queue_worker_with passes a JobControl to the handler as well:

  • job.idle() says the job will mostly wait from now on (on a slow remote service, a human): it stops counting against the concurrency limit, so the worker takes other jobs, while its lease keeps being renewed.
  • job.throttle(pause, reason) says the service behind the worker is overloaded: claiming pauses for pause and an adaptive limit halves.

Shutdown and drain deadlines

The worker runs until the Notify you passed is notified (use notify_one). It then stops claiming, hands back anything it claimed but has not started, gives up its place in line, and waits for running handlers.

  • Without .drain(…) it waits for every handler, however long.
  • With .drain(d), handlers still running after d are dropped at their next .await and their jobs are failed with the default backoff — or released to run again at once with .release_drained(). They are never reported complete. Handlers stuck outside an .await five seconds later are abandoned and come back when their lease lapses.

Pair drain with your platform's termination grace period: if Kubernetes waits 30 seconds after SIGTERM, drain for 20.

When the worker gives up

Transient failures — network errors, timeouts, overload, no leader — never end a worker; it waits and tries again. A refusal the same request would meet again ends it with that error: revoked credentials (Auth), an unknown database, invalid options (Server { code: "invalid_options" }). queue_purging does not: when the last module declaring a queue is removed and purged, the queue refuses every operation until the purge has deleted it, and the worker waits that out like a transient failure (FlowerError::is_transient says so), while the module listing (cargo flower modules) shows the module purging. Run workers under a supervisor that restarts them and alerts on repeated exits.

External values with reconcile

Some values are computed outside Flower — a word count from a service, a price from a supplier — but should behave like derived values. A guest declares an external value with flower_sdk::external!: an input computed from the database, and a contract for the result. Listed among the app's components, it brings its collections, its trigger and the operations workers use; the http option (external!(.., http)) is what lets a worker reach those operations over HTTP, and the authorization component's methods table gives them access other than the default (("words.publish", Access::Check(worker))). The reconcile worker watches for inputs that changed, calls your function with each, and publishes the result back; a result for an input that has since changed is rejected and recomputed. It runs for one key (.args(…)), drains a pool of stale keys, or splits a pool between processes under leases (.leased()). The repository's examples/external-transactions guest and crates/flower-worker/tests/reconcile.rs show both sides.

Testing workers

With the testing feature, flower_worker::testing::FakeQueue is an in-memory queue with the server's claiming rules on Tokio's clock, so worker tests run in paused time without a server. See Testing applications.

Typed payloads and lease handles

run_typed_queue_worker accepts a TypedQueue<Payload, Result> descriptor and passes a decoded TypedJob<Payload> to the handler. The worker renews and settles the lease automatically; incompatible payloads are dead-lettered. Manual workers use claim_typed and its lease handle for heartbeat, typed completion, failure and release, with the database, queue, claim token and fence already bound.

Manual claims return one ClaimOutcome<Payload, Result> per item, so an incompatible payload never discards other claims. A decoding error retains the raw payload and its lease. Terminal operations consume the lease; a SettlementError returns it via into_lease() for explicit retry under the same claim identity. Heartbeat borrows the handle. Dropping a settlement future or lease performs no network cleanup; its server lease expires normally. Use request cancellation and await the error when ownership must be recovered.
