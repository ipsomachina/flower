Guides

Operating a cluster

One binary serves every member: cargo flower serve. This guide covers running three of them, the credentials they need, changing membership, watching health and load, upgrading Flower, and the knobs worth knowing.

A three-node cluster

Three voters tolerate the loss of one. Give each member its own directory, ID, HTTP address and Raft address, and the same tokens. Only the founding member gets --bootstrap, naming every member's Raft address:

export FLOWER_ADMIN_TOKEN=… FLOWER_WORKER_TOKEN=… FLOWER_PEER_TOKEN=…

# on host a
cargo flower serve --dir /var/lib/flower --id 1 --http 0.0.0.0:8080 --raft 10.0.0.1:9000 \
  --advertise-http https://a.flower.internal:8080 \
  --bootstrap 1=10.0.0.1:9000 --bootstrap 2=10.0.0.2:9000 --bootstrap 3=10.0.0.3:9000
# on host b
cargo flower serve --dir /var/lib/flower --id 2 --http 0.0.0.0:8080 --raft 10.0.0.2:9000 \
  --advertise-http https://b.flower.internal:8080
# on host c
cargo flower serve --dir /var/lib/flower --id 3 --http 0.0.0.0:8080 --raft 10.0.0.3:9000 \
  --advertise-http https://c.flower.internal:8080

On one machine, with loopback addresses and ports 18091–18093, the same three commands give:

id=1 state=Leader leader=Some(1) term=2 last_log=Some(1) last_applied=Some(1)
id=2 state=Follower leader=Some(1) term=2 last_log=Some(1) last_applied=Some(1)
id=3 state=Follower leader=Some(1) term=2 last_log=Some(1) last_applied=Some(1)

A write sent to a follower is forwarded to the leader; its Server-Timing shows the hop and which member led:

server-timing: forward;dur=4.1, admission;dur=0.0, queue;dur=0.0, eval;dur=0.6, commit;dur=3.2, append;dur=0.1, replicate;dur=2.5, apply;dur=0.3, total;dur=4.2, node;desc=3, leader;desc=1
x-flower-leader-url: http://127.0.0.1:18091
  • --bootstrap takes effect only on an empty directory. Restarting any member with the same command line is always safe.
  • --advertise-http is the URL clients should use to reach this member; it appears in x-flower-leader-url. It defaults to the listen address, except when listening on all interfaces.
  • Use the same timing settings on every member.
  • On shutdown (Ctrl-C or SIGTERM), a member hands leadership of every group it leads to the most caught-up voter, then drains HTTP requests for --shutdown-timeout-ms (30 s).

Credentials and TLS

FlagEnvironmentGrants
--admin-tokenFLOWER_ADMIN_TOKENOperator endpoints (deploy, membership, keys, backups, metrics…), the worker and sync endpoints, and trusted-gateway calls. Without it, operator endpoints always answer 403.
--worker-tokenFLOWER_WORKER_TOKENThe queue endpoints, for workers.
--sync-tokenFLOWER_SYNC_TOKENReplica sync, for devices.
--peer-tokenFLOWER_PEER_TOKENRaft between members. Defaults to the admin token; required whenever --raft is not loopback.
--key-wrapping-fileFLOWER_KEY_WRAPPING_FILENot a token: the 32-byte key sealing every database's managed-key catalog. Mount the same file on every member of every group. A member without it serves no catalog key (KEYS_LOCKED), and a partition move to a group it leads waits until it can. To replace it, start members with the new file and the old one as --key-wrapping-previous, then run cargo flower keys --db … rewrap.

Client commands read the server's address from --endpoint, or FLOWER_ENDPOINT, defaulting to http://127.0.0.1:8080, and the admin token from FLOWER_ADMIN_TOKEN. Application calls need no server token; modules authenticate their own users (see Authentication). For TLS on the API, pass --tls-cert and --tls-key (PEM): every connection is then TLS 1.2 or 1.3, HTTP/2 by ALPN, with no plaintext fallback. For TLS between members, pass all three of --raft-tls-cert, --raft-tls-key and --raft-tls-ca on every member. The API serves HTTP/1.1 and HTTP/2 on one port; there are no CORS headers, so browsers must call through your own origin.

Changing membership

cargo flower membership without --members prints the member's view: leader, voter sets and addresses. With --members, it sends the leader the complete desired voter set:

export FLOWER_ENDPOINT=https://a.flower.internal:8080
cargo flower membership \
  --members 1=10.0.0.1:9000 --members 2=10.0.0.2:9000 --members 3=10.0.0.3:9000 --members 4=10.0.0.4:9000

The leader checks every member's identity and software compatibility, refuses a new member that already holds Raft state, waits for new members to catch up, and switches through joint consensus. A change is bounded to 15 seconds; a refused or uncertain one exits non-zero (409 membership) and may have partly happened, so inspect before retrying, and pass --expected-log-id to make a change conditional on the membership you inspected.

  • Add a member by starting it with an empty directory and no --bootstrap, then including it in --members.
  • Remove one by leaving it out (--retain keeps it as a non-voting learner).
  • Replace a dead member under a fresh ID: an ID cannot move to another address.
  • Move leadership before maintenance with cargo flower leadership --to 2, sent to the leader; writes answer a retryable 503 leadership_transfer for the moment it takes.

Health, readiness and status

EndpointUse
GET /health/liveLiveness: 200 {"ok":true} while the process serves.
GET /health/readyReadiness: 200 when the member knows a leader, has applied what it knows is committed, is not rejoining and has no storage failure; 503 with a reason otherwise. A process hosting several groups is ready only when all are.
GET /v1/statusRaft state: {id, state, leader, term, last_log, last_applied} (cargo flower status).
 
{"applied":1,"committed":1,"leader":1,"ok":true,"reason":null,"rejoining":false,"storage":null}

Route load balancer traffic by readiness. A member that lost its data, or restarted after an unsynced crash, comes back rejoining: unready, casting no votes and refusing replica-local reads until it has caught up with its leader.

Metrics, timing and tracing

  • Server-Timing on every query, mutation and transaction answer breaks the request into phases: forward, cache, fence, join, admission, queue, eval, commit, append, replicate, apply, total, plus the answering node and the leader. Always on, and visible in browser dev tools.
  • GET /v1/metrics (admin; cargo flower metrics): per-database revisions, admission and shedding, reads (lease reads, quorum rounds, forwards), the writer, retention, deployments, snapshots, compaction, query cache, authorization decisions, Wasm pools and per-method costs.
  • OpenTelemetry: set FLOWER_OTEL_ENABLED=1 and the standard OTEL_EXPORTER_OTLP_* variables (HTTP protobuf or JSON; no gRPC). Spans join an incoming traceparent and follow forwards; metrics are named flower.http.*, flower.query.*, flower.writer.*, flower.evaluator.*, flower.storage.*, flower.raft.* and flower.watch.*. Request bodies, arguments and credentials are never exported. Logs follow RUST_LOG (default info).

The admin dashboard

Every member serves a dashboard at /admin on its API port: Raft and readiness, replication, databases and modules, queues, deployments and stagings, backups, retention and live activity. It asks for the admin token, keeps it for the tab only, and talks only to its own origin. Actions that change things — taking a backup, transferring leadership, advancing or activating a staging — ask for confirmation. Turn it off with --admin-ui false. The same data streams as server-sent events from GET /v1/admin/stream.

Overload

Flower refuses work it cannot do in time rather than queueing without bound. A refused request answers 503 overloaded with Retry-After; nothing ran, so clients retry after the delay (the Rust client does). Requests carrying x-flower-timeout-ms are shed as soon as they could no longer finish within it (503 caller_deadline_exceeded), and a write still queued at its deadline never runs. Writes never queue behind reads, and each database gets a fair share of each queue.

FlagDefaultMeaning
--query-workersCPU countConcurrent query and watch evaluations.
--queued-input-bytes64 MiBRequest bytes queued or running.
--admission-max-wait-ms10,000Longest wait for admission before refusing.
--admission-target-ms / --admission-interval-ms50 / 500Queueing-delay target for early shedding of requests with deadlines.
--writer-preparation-workersmin(CPUs, 8)Threads preparing mutations speculatively.
--guest-timeout-ms5,000The deadline of a call whose method declares no timeout.
--guest-max-timeout-ms60,000The longest deadline a method may declare; longer declarations run to this.
--guest-memory-bytes128 MiBMemory one guest instance may reach.
--max-transaction-bytes32 MiBThe largest effects one write may commit; larger ones fail 413 transaction_too_large before anything is proposed. Checked at startup against --raft-max-frame-bytes (it must fit four times over), and when a peer dials.

The guest flags bound wall-clock time and memory only. A call's instruction budget follows from its method's declared deadline, the same on every member, so a call that fits on one member fits on all.

Durability and storage

  • --fsync on (the default) makes every acknowledged write durable on a quorum. off survives process crashes but not power loss.
  • With three or more voters, the leader defers its own log flush while followers alone form a majority (--leader-flush lazy, the default): one fsync per write on the critical path.
  • Snapshots are taken every 10,000 entries, after 16 MiB applied or after 5 minutes; data files compact themselves online. The defaults suit most deployments.
  • If storage fails, the member stops accepting writes and linearizable reads (503 storage_failed), reports unready, and once the disk accepts writes again exits non-zero so its supervisor restarts it. Acknowledged writes are not lost: they live on a quorum.

Upgrading Flower

Every member carries a compatibility contract: how entries apply, how snapshots and values encode, how peers frame messages, and the Wasm engine. cargo flower membership prints each member's:

compatibility=wire7-state12-snapshot1-value4-wasmtime-49.0.0 build=0.1.0
  • Same contract, new build (a bugfix release): roll the cluster one member at a time — move leadership away, stop the member, start the new binary on the same directory, wait for it to be ready. Members of one contract join each other whatever their build.
  • Another contract: members of different contracts refuse each other's connections, and a member refuses at start to open files another contract wrote (incompatible_store, naming both contracts). There is no in-place upgrade across a contract change: take a backup with the old build, stop every member, and restore it with the new build into fresh directories.

Read the release notes for a contract change before upgrading, and keep the old binary until the new cluster serves.

Raft timing and read leases

The timing flags derive from --raft-rtt-ms, the round trip between the farthest members (0 on a LAN). With the defaults — 50 ms heartbeats, a 300 ms leader lease, 100–200 ms election timeouts and a 270 ms read lease — a failed leader is replaced in about half a second. Across regions, set --raft-rtt-ms to the measured round trip and let the rest follow. --raft-read-lease-ms 0 disables read leases, making every linearizable read take a quorum round (see Leader leases). Use identical timing on every member.

Groups and partitions

cargo flower group create east --members 2,3,4
cargo flower partition create acme --group east
cargo flower partition move acme --to west --wait
cargo flower partition resize --groups east,west --op balance-2026-11
cargo flower group prefer-leader west --node 3 --op west-on-3
cargo flower partition          # list
cargo flower transactions       # cross-group transactions in flight
  • A group runs on a subset of the root group's members; every server process is a root member.
  • partition create places a database on a group — adopting it in place if it already exists in root. Clients keep using the database name.
  • partition move copies the database while it serves, freezes it briefly, and cuts over; calls during the freeze answer 503 partition_moving. A move that cannot freeze within --partition-freeze-max-ms (30 s) aborts on its own; partition abort stops one by hand. The database's managed-key catalog moves with it.
  • partition resize balances partition counts over the named active groups. It persists the plan and starts durable moves; inspect them with partition. Retrying the same --op returns the original plan. Finish pending partition operations before starting another resize.
  • New groups spread their preferred leaders over their members. group prefer-leader selects a voter, or disables placement for that group when --node is omitted. Placement waits for the target to catch up and suspends during catalog outages. serve --leader-placement off disables it on a host.
  • Every change takes an --op ID (defaulting to the operation and name), so repeating a command is safe.
