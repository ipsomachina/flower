Backups and restore

Every member can archive the log continuously into an encrypted backup store — an S3 bucket or a directory. Restore offline to the latest backup, to a named backup, to an exact log position, or to a point in time.

How it works

  • The group's leader periodically takes a base (a full snapshot) and continuously archives the log entries applied after it, in segments. A restore loads a base and replays archived entries.
  • Every object is compressed (zstd) and sealed with AES-256-GCM under a backup key kept in a keystore file, itself sealed by a 32-byte key-encryption key (KEK) you provide. Object names are opaque.
  • Every member runs the backup loop with the same configuration. Members hold log entries they would otherwise purge until the archive has them (the purge hold), so a new leader continues the same archive without starting over.
  • Retention is by time: every point of the last 30 days stays restorable (--backup-retention-ms); older bases are thinned to one per base interval, and segments no kept base needs are deleted.

Configure continuous backup

Give every member the same three settings: where backups go, a keystore file and the KEK file. In S3:

head -c 32 /dev/urandom > backup.kek          # keep it outside the backup store
export FLOWER_BACKUP_S3_REGION=eu-central-2     # else AWS_REGION, and so on
cargo flower serve --dir data --id 1 --bootstrap 1 --admin-token secret \
  --backup-url s3://acme-backups/flower --keystore /etc/flower/backup.keystore --kek-file /etc/flower/backup.kek

S3 reads its settings from FLOWER_BACKUP_S3_REGION, FLOWER_BACKUP_S3_ENDPOINT (for another S3 implementation), FLOWER_BACKUP_S3_ADDRESSING (path or virtual) and FLOWER_BACKUP_S3_ACCESS_KEY_ID, …_SECRET_ACCESS_KEY and …_SESSION_TOKEN; each falls back to its AWS_ name, and the credentials to AWS's usual chain. Large objects go up as multipart uploads. To back up to a directory instead — shared storage, or one you copy elsewhere — pass --backup-dir /backups/flower (or --backup-url file:///backups/flower).

If the store is unreachable for long, the purge hold grows the log; past the caps, the oldest entries go unarchived, the next base starts a new archive, and point-in-time targets inside the gap can no longer be restored. Without caps, the log grows until the disk fills. Groups other than root back up under groups/<name> inside the same location, with keystore <keystore>.<name>, sealed by the same KEK.

export FLOWER_ADMIN_TOKEN=secret
export FLOWER_BACKUP_URL=s3://acme-backups/flower FLOWER_BACKUP_KEYSTORE=/etc/flower/backup.keystore FLOWER_BACKUP_KEK_FILE=/etc/flower/backup.kek

cargo flower backup             # take a full backup now, through the member at FLOWER_ENDPOINT

Restore

Restore is offline: stop the member, restore into its directory, start it again with --bootstrap. To restore a whole cluster, stop every member, restore the same target on each, and start them together.

# with FLOWER_BACKUP_URL, FLOWER_BACKUP_KEYSTORE and FLOWER_BACKUP_KEK_FILE set as above
cargo flower backup restore --dir data                          # the newest state the backups hold
cargo flower backup restore --dir data --at-ms 1793491200000    # the state at a time
cargo flower backup restore --dir data --index 48211            # exactly through a log index
cargo flower backup restore --dir data --manifest <manifest>    # one backup, as taken

cargo flower serve --dir data --id 1 --bootstrap 1 --admin-token secret --key-wrapping-file wrapping.key
restored backup_id=d004740955c0e17b282e95e7a5f9a94d manifest=flower-backup/v1/manifest/ac91a3ee68e13e9630bbb00e1b1c8bf6 history=f5af2bdc0a20ad75 index=46 replayed=1 reached_ms=1793543023251
start the node with --bootstrap to serve the restored state
  • Without a target, the newest state the backups hold: the latest base, then every entry archived after it. --manifest restores one backup exactly as it was taken.
  • --at-ms replays every write stamped at or before that time: the result is at or just before the target, never after it.
  • --index counts in one history; pass --history (as list prints it) to pick another than the latest backup's.
  • Restore registers every module again, so pass the same --guest-* limits the cluster runs with.
  • Each database's managed-key catalog is restored with it, still sealed: start the restored members with the same --key-wrapping-file, or managed keys answer KEYS_LOCKED.
  • The restore replaces the group file and removes the Raft log, so the member starts a new log over the restored state: start it with --bootstrap, and for a cluster bootstrap the restored members together, as when you founded it.

After a restore

A restore to an earlier point starts a new history of each database, with a fresh incarnation:

  • Scoped request IDs (f1:/f2:), retry sessions and queue claims minted in the old history are refused with wrong_history; plain idempotency keys replay from restored receipts.
  • Log positions restart; synced device replicas see HistoryChanged and must rebuild.
  • Everything after the target is gone — including work your workers already did in the outside world. Fence the old deployment (it keeps running if you restored elsewhere), and reconcile external effects.
  • Groups restore independently: a restore is not atomic across groups.

Upgrades across a compatibility contract A member refuses to open data files written under another compatibility contract, so a Flower upgrade that changes the contract cannot reuse a member's directory. A backup is the way across: take one with the old build, stop every member, restore into fresh directories with the new build, and bootstrap. See Upgrading Flower.
