Errors and retries in clients

Every failed call falls into one of three cases: the application said no, nothing ran, or you cannot tell. Retrying is only right in the last two, and in the last one only with the same request ID.

Three cases

CaseWhat you see over HTTPWhat to do
The application said no 422 with "ok":false: the call's own failure, for queries, mutations and transactions alike. Your method's code, message and details; INVALID_ARGUMENT with details.path for arguments that do not match; stale_revision; deadline_exceeded when the call ran past its own declared deadline. Also 403 (authorization), 404 UNKNOWN_METHOD, 400 bad_request (malformed body), 413 (too large) and 415 (no JSON content type). Never retry blindly: the same request gets the same answer. Show it, or fix the call.
Nothing ran 503 with overloaded (and Retry-After), caller_deadline_exceeded (your own deadline passed first), quorum, forward, recovering, rejoining, stale_replica, storage_failed, leadership_transfer, partition_moving, instantiation_failed, module_unavailable; a 429 from an operator stream. Retry after a delay, honouring Retry-After; another member may answer sooner.
You cannot tell A timeout, a dropped connection, a cancelled request, 503 leader_isolated, 503 forward_failed. A write may have committed. Retry with the same request ID: if it committed, the retry answers the original outcome with "duplicate": true.

Queries never change anything, so they are always safe to retry. Mutations and transactions are safe to retry with their request ID — which is why you should give every write one.

Over HTTP, the bodies look like this (all live answers):

{"ok":false,"revision":10,"position":32,"code":"INSUFFICIENT_FUNDS","message":"the balance is too low","details":10,"duplicate":false}   // 422
{"code":"INVALID_ARGUMENT","details":{"path":["amount"]},"message":"arguments for `transfer` invalid at $.amount: integer below minimum","ok":false}   // 422
{"ok":false,"revision":12,"position":48,"code":"stale_revision","message":"expected revision 3 but the database is at 12","duplicate":false}   // 422
{"code":"UNKNOWN_METHOD","message":"`methods` has no `nope` callable over HTTP (declared `http`)","ok":false}   // 404
{"code":"UNKNOWN_METHOD","message":"database `bank` has no module `nomod`","ok":false}   // 404
{"code":"UNKNOWN_METHOD","message":"no database `nowhere` here","ok":false}   // 404
{"code":"bad_request","message":"Failed to parse the request body as JSON: EOF while parsing a value at line 1 column 12","ok":false}   // 400
{"code":"caller_deadline_exceeded","message":"the caller's deadline passed","ok":false}   // 503

A mutation's own failure carries the revision and log position its failed outcome was recorded at; a failure decided before the call ran, such as INVALID_ARGUMENT, carries neither.

What flower-client does for you

With retries on (.retry(Retry::Default) on the builder, or RequestOptions::retrying() / MutationOptions::retrying() per call), the client:

  • retries transport errors, attempt timeouts, 429, 502, 504 and every 503 except forward, up to 8 attempts with equal-jitter exponential backoff from 250 ms to 30 s;
  • retries overload refusals on their own budget — 60 seconds by default, not counted against the attempts — waiting at least what Retry-After asks;
  • sends the same request ID, and the same body, on every attempt of a mutation;
  • never retries a 200 or a 422 (so never a business failure), a 401 or 403, or any other status;
  • stops at the call's deadline and when its CancellationToken fires.

RetryPolicy tunes all of it: attempts, delays(initial, max), attempt_timeout, until(instant), through_overload and overload_budget. client.overloads() counts the load refusals seen so far, which is a good signal to slow down.

The error type

Every call returns Result<_, flower_client::FlowerError>:

VariantMeaning
Business { code, message, revision, position, details }The call's own failure, and only that: a 422 answer carrying the "ok":false envelope, from a query, a mutation or a transaction.
Server { code, message }Any other non-2xx answer: UNKNOWN_METHOD, bad_request, a failure of the server itself. A body that is not JSON (a proxy's page, the 413 body limit) gives code: "status 413" and the text.
Auth(_)401 or 403. The server's body (unauthorized, ACCESS_DENIED…) is not kept.
RetryExhausted(_)Retryable refusals until the policy gave up — or the first one when retries are off.
Forward { leader }The member could not reach any leader.
Timeout, Transport(_), CancelledNo answer: unknown outcome for a write.
Decode(_)The answer did not decode into the type you asked for.
HistoryChanged, Engine(_)Offline replicas only.
 
/// What a failed call means for the caller.
pub fn advice(error: &FlowerError) -> &'static str {
    if error.is_auth() {
        return "credentials refused";
    }
    if error.execution() == flower_client::Execution::Unknown {
        return "outcome unknown: reuse the persisted command and its request ID";
    }
    if error.is_transient() {
        return "retry with the same identity after the server's retry hint";
    }
    match error {
        // The call's own failure (HTTP 422): a declared error, bad
        // arguments (INVALID_ARGUMENT), its own deadline passing
        // (deadline_exceeded). Final; show it, don't retry it.
        FlowerError::Business { .. } => "the application said no",
        // 401/403: the hook or an access rule refused the caller.
        FlowerError::Auth(_) => "credentials refused",
        // The write may or may not have committed.
        FlowerError::Timeout | FlowerError::Transport(_) | FlowerError::Cancelled => {
            "unknown outcome: retry with the same request ID"
        }
        // Legacy transport errors; structured HTTP errors retain certainty separately.
        FlowerError::RetryExhausted(_) | FlowerError::Forward { .. } => "try again later",
        // A refused request (unknown alias, malformed body, too large)
        // or a server failure: a bug or a misconfiguration, not a
        // transient state.
        FlowerError::Server { .. } | FlowerError::Decode(_) => "fix the call",
        _ => "see the error",
    }
}

Declared errors decode into the method's own error enum when you call through its descriptor (client.call, or the *_declared calls); see typed calls. A variant marked #[flower(retryable)] answers true from its generated is_retryable() — use it for application-level "try again" answers such as a transient upstream condition the method reports.

Request IDs across restarts

The client's retries happen within one call. If your process can crash between sending a write and learning its outcome, the request ID must outlive the process: derive it from the intent, store it with the intent, and send it again on restart. A scoped ID from retry_identity adds a server-side check that a reused ID carries the same request:

pub async fn checkout(
    client: &FlowerClient,
    cart: &str,
) -> Result<MutationResult<serde_json::Value>, FlowerError> {
    let identity = client
        .retry_identity("shop", &RequestOptions::new())
        .await?;
    // The same intent gives the same ID within the retry window; store
    // it with the cart before sending, and resend it after a crash.
    let id = identity.request_id(format!("checkout:{cart}").as_bytes());
    let options = MutationOptions::retrying().request_id(id);
    client
        .mutate_value("shop", "shop", "checkout", &json!({"cart": cart}), &options)
        .await
}

Receipts last for the database's retry window — by default 24 to 27 hours. A retry after that runs as a new write.

Stale revisions

A mutation sent with expected_revision fails with Business { code: "stale_revision", revision, .. } when the database has moved on; the error's revision is the current one. Retrying the same request can never succeed: re-read, decide again, and send a new request.

From other languages

Any HTTP client works the same way. Send Content-Type: application/json, put a stable idempotency_key in every write's body, and set x-flower-timeout-ms to the time budget. Inspect the structured problem's origin, execution certainty and retry advice alongside status and code. A 422 can report a declared application error, SQL validation or budget failure, or another host refusal; status alone does not identify a declared error. The request-body limit's 413 can answer in plain text. The HTTP reference lists the endpoints and response fields.
