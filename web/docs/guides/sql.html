SQL queries

Run bounded, read-only SQL through ordinary module queries. Declare a typed plan for a fixed statement, or a scoped endpoint for statements supplied at request time.

Request-time SQL

A SqlEndpoint fixes the local collections a statement may read and its resource ceilings. A wrapping query chooses the public name and access rules. The endpoint itself creates no HTTP route. SQL reads the invocation's pinned snapshot, sees staged writes, and applies the enclosing authority's row and field policies.

This application exposes sql, sql_explain, a typed orders_by_owner query and a mutation for inserting orders. The #[application] macro assembles its lexical collections and methods; #[component] registers the SQL declarations. Export shop::APP from your guest crate's root.

For manual composition, use App::new and list the collection, endpoint, named plan and method descriptors explicitly. HTTP exposure and authorization remain properties of the wrapping methods.

Build, deploy and execute

The repository includes a complete sql-queries guest. With a server running, set FLOWER_ADMIN_TOKEN for deployment and FLOWER_TOKEN for application calls as required by your server and module.

cargo flower build --package sql-queries --profile dev
cargo flower deploy --db demo --module shop --wasm .flower/sql-queries.wasm
cargo flower call --db demo --module shop --name put_order --mutation --args-file order.json
cargo flower call --db demo --module shop --name sql --args-file query.json
cargo flower call --db demo --module shop --name sql_explain --args-file query.json

Contents of order.json for the repository example:

{"id":"one","order":{"owner":"ada","status":"open","total":"9007199254740993"}}

Contents of query.json:

{"statement":"SELECT _key AS id, total FROM orders WHERE owner = :owner ORDER BY total DESC LIMIT :limit","params":{"owner":"ada","limit":10}}

--args-file - reads standard input. Add --contract .flower/sql-queries.manifest.json to validate the public method and argument shape locally. SQL syntax and binding are checked by the host when it executes the module query. Over HTTP, use the same arguments with POST /v1/query; there is no separate administrative SQL endpoint.

Parameters and result contracts

SqlQuery<P, R> binds its statement and parameter/result schemas at deployment. run(ctx, &params) returns Vec<R>. Each plan is a component and must be registered.

SqlEndpoint::run accepts any FlowerType parameter object, including Value, and returns projected JSON objects. run_as<R> decodes rows into a chosen result contract. Supply exactly the named parameters the statement uses, with an empty object or null when none are needed. The dynamic binder infers types from values and column comparisons. Decimal columns require exact decimal strings; a JSON number cannot substitute for one.

Explicit null and absent data remain distinct. Redacted or absent projected fields are omitted; typed response fields that may be absent should use Omittable<T>. SQL predicates on absent/redacted fields are unknown, including IS NULL. Visible null values follow SQL null semantics. Field policies also apply before comparisons and sorting.

Supported dialect

Statements select from one local collection, using * or projections, aliases, named parameters, comparisons, IS NULL, IS NOT NULL, AND, OR, NOT, ordering and a mandatory LIMIT. Access the primary key with _key, tuple keys with _key[n], and declared nested fields through paths. LIMIT must be between 1 and 10,000.

Ordering follows logical values, including exact decimal integers, with a deterministic key tie-breaker. Joins, aggregates, arbitrary functions, writes and continuation cursors are not implemented. Results are complete for the statement's limit at one snapshot.

Access paths and limits

The planner can use primary-key equality, a complete secondary-index equality bucket, or a bounded collection scan. require_index() rejects a named plan at deployment, or a dynamic statement at execution, when no supported index path is proven. Legacy index ordering does not support SQL range pushdown or partial-prefix optimization.

SqlBudget::new(candidates, bytes, work) configures positive ceilings. scan remains an equivalent constructor. Maxima are 10,000 candidates, 64 MiB and 10,000,000 work units. Hidden rows still count; LIMIT bounds returned rows and does not bound scan input. Dynamic parsing and binding consume the endpoint's budget. Statements are limited to 16 KiB and named parameter objects to 64 members. Exhaustion fails the operation rather than returning a partial result.

Explain and diagnostics

Both handles offer explain returning Value and explain_typed returning SqlExplain. The typed view includes the access path, collection, proven input bound and resource ceilings, and retains extension fields in raw. Dynamic explain binds the supplied parameters without reading rows; its execution ceilings reflect the remaining budget after binding.

cargo flower sql-explain --manifest .flower/sql-queries.manifest.json --plan orders.open

The CLI command explains a named plan offline. For a request-time statement, call the module's sql_explain query.

SQL_INVALID covers syntax, binding and unsupported access paths. Parser diagnostics include zero-based UTF-8 start_byte and exclusive end_byte; end-of-input failures have an empty span. SQL_BUDGET reports exhaustion; evaluator failures identify the dimension in details.budget. Parameter contract errors use INVALID_ARGUMENT. An endpoint scope refusal uses ACCESS_DENIED.

Compatibility

SQL host operations and decimal schemas require state-machine compatibility version 10. The stored value format remains 4. Existing store-contract checks require backup/restore into a fresh directory across a contract change; see the upgrade procedure. Value-ordered indexes, snapshot-retaining pagination and cross-group recovery changes remain future work.
