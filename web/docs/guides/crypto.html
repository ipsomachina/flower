Guest cryptography

Guests hash, sign, verify, encrypt and run passkey ceremonies through the host: no primitive runs in Wasm, and managed secret keys never enter guest memory. Each database keeps its keys in a replicated catalog that operators provision and rotate.

The crypto host

Every server runs guest crypto: hashing, randomness, JWTs and JWEs with keys the guest supplies, and WebAuthn need no configuration. Every operation goes through ctx.crypto(), which query, mutation and derived contexts all offer; it borrows the context, so create one, use it and drop it. Bytes are plain Rust slices; hex_encode/hex_decode and webauthn::base64url_encode/base64url_decode convert for the wire. Crypto failures are ordinary failures you can map to your own codes, not traps.

Managed keys are the one part that needs an operator. Each database's catalog is sealed by a 32-byte wrapping key that every member mounts:

head -c 32 /dev/urandom > wrapping.key        # keep it secret, back it up
cargo flower serve --dir data --id 1 --bootstrap 1 --admin-token secret \
  --key-wrapping-file wrapping.key

A member started without one still applies the catalogs it replicates, but serves no catalog key: guests calling a managed key there fail KEYS_LOCKED, and key changes sent to it answer 503 KEYS_LOCKED: retry once a member that has the key leads. Everything else keeps working.

Hashing and randomness

Everything except randomness is deterministic, so queries, derived values and authorization hooks can hash, verify and decrypt. random_bytes (at most 1,024 bytes a call) and anything that draws randomness — key pairs, WebAuthn challenges, JWE without an explicit nonce — works only in mutations; elsewhere it fails with INVALID_INVOCATION. A mutation's random output is decided once on the leader and replicated, like the rest of its effects.

Managed keys

A module declares the keys it uses by an alias, an algorithm and the usages it needs. An operator generates (or imports) a key in the database's catalog and binds it to that alias, granting usages. Both sides must agree: an undeclared alias fails FORBIDDEN_USAGE, an unbound one UNKNOWN_KEY (managed key "tickets" is not bound).

The operator side, with the admin token, names the database whose catalog it changes (--db, before or after the subcommand):

export FLOWER_ADMIN_TOKEN=secret
cargo flower keys --db app generate --name ticket-signing --algorithm Ed25519
cargo flower keys --db app generate --name vault-2026 --algorithm A256GCM
cargo flower keys --db app bind --alias tickets --key ticket-signing --usages sign,verify,publicKey
cargo flower keys --db app bind --alias vault --key vault-2026 --usages encrypt,decrypt
cargo flower keys --db app

Each change prints its request ID and the catalog's new revision, then the catalog; the listing alone is:

key=ticket-signing algorithm=Ed25519 active=1 versions=1:live
key=vault-2026 algorithm=A256GCM active=1 versions=1:live
binding=tickets key=ticket-signing usages=publicKey,sign,verify
binding=vault key=vault-2026 usages=decrypt,encrypt

A change is replicated through the database's group and runs under a request ID: pass --request-id to retry one safely. keys import seals existing key material locally with the wrapping key before sending it, so it never travels in the clear. Without --db, keys lists every database's catalog.

To separate offline preparation from online import, seal on the machine holding the wrapping key, then import the envelope on an operator machine:

cargo flower keys seal --key-file private.key --wrapping-file wrapping.key --out sealed.json
cargo flower keys --db shop --request-id import-boxes import --name boxes --algorithm X25519 --sealed-file sealed.json

Concurrent cold uses of the same managed key share one native preparation when the coordination fits --key-cache-bytes. Full or zero budgets fall back to independent preparation without refusing crypto. Each call still checks the current binding and lifecycle; the cache grants no authority.

Managed X25519 keys also support crypto.nacl().box_before_managed(&peer, &key, ManagedKeyRef::Current). It returns a non-exportable shared-key handle for box_after and box_open_after. Derivation requires derive; each use additionally requires encrypt or decrypt. Handles live only for that invocation, share a 1 MiB native memory budget, and cannot be serialized. Rotation stops old handles encrypting while allowing decryption; revocation stops both.

Rotation. Each key has numbered versions, one active. keys rotate adds a new active version; signing and encrypting use it from then on. Older versions keep verifying and decrypting until an operator retires (verify and decrypt only), revokes (nothing) or destroys them. JWTs carry the version in their kid (flower.<key id>.<version>), so tokens issued before a rotation keep verifying.

Isolation. Each database has its own catalog. A key generated and bound in app does not exist in any other database, even one in the same group: the same module deployed into another database answers UNKNOWN_KEY until that database's own catalog binds the alias.

Results that used a managed key are never served from the query cache, and any catalog change re-evaluates derived values, watches and authorization decisions that used a key — so revoking a key takes effect everywhere at once.

Signed tokens (JWT)

A ticket's protected header names the binding's algorithm and the version that signed it:

{"alg":"EdDSA","kid":"flower.kVmQNyYF7VeHo0uqfYzyIQ.1","typ":"JWT"}
{"ok":true,"value":"ada"}                                                       // ticket_holder
{"ok":true,"value":{"kid":"flower.kVmQNyYF7VeHo0uqfYzyIQ.1","x":"sOCdOyVfLhz-zEL-F7eeTRE2geKUoQQXNi9hjGUlbAE"}}   // ticket_key
  • With a managed key, the binding fixes the algorithm and the kid. With raw keys — JwtKey::Bytes(secret, KeyFormat::Raw) for HS256 (at least 32 bytes), KeyFormat::Der or JwtKey::Pem for public keys — signing needs SignOptions::algorithm and verifying a non-empty VerifyOptions::algorithms allowlist: the token's own alg never decides.
  • Verification checks exp (required unless require_expiration: Some(false)), nbf, and, when you ask, iss, sub and typ. The audience must be validated explicitly: a token carrying aud fails unless you set audience. Check custom claims yourself.
  • Verification does not poll the clock. It declares when its answer changes — at exp for a valid token — so a query checking a token is cached, and its watches hold, until then.
  • Failures come back as CRYPTO_ERROR with messages such as JWT expired; map them to your own codes, as ticket_holder does.

Encrypted tokens (JWE)

Only compact dir + A256GCM is supported, with a managed A256Gcm key or a raw 32-byte key. Pass an explicit 12-byte nonce to encrypt outside a mutation, and never reuse one under the same key. decrypt validates standard claims like verify.

Passkeys (WebAuthn)

A WebAuthn ceremony takes two mutations: one creates options with a fresh challenge and stores it, the other consumes the challenge and verifies the browser's response.

begin_registration returns PublicKeyCredentialCreationOptionsJSON for the browser:

{"attestation":"none","authenticatorSelection":{"requireResidentKey":true,"residentKey":"required","userVerification":"required"},
 "challenge":"_hMdwFGw8RlggxK4GkP2HjWBfOWnNbAIqt2x48x_mZQ","excludeCredentials":[],
 "pubKeyCredParams":[{"alg":-8,"type":"public-key"},{"alg":-7,"type":"public-key"},{"alg":-257,"type":"public-key"}],
 "rp":{"id":"example.com","name":"Example"}, …}
  • The option builders default to discoverable credentials, required user verification and no attestation, offering EdDSA, ES256 and RS256. RegistrationOptions::new defaults to preferred user verification, so set it to match the options, as above.
  • The host checks the challenge, the exact origin, the RP ID hash, user presence and verification, the credential algorithm and the signature. Attestation statements other than none are not evaluated.
  • Store sign_count after each sign-in. If the stored or new counter is non-zero, the new one must be greater, or verification fails with WEBAUTHN_COUNTER (a possibly cloned authenticator). Synced passkeys usually report zero.
  • Challenges must be single-use. The host only compares; deleting the stored challenge, as the mutations above do, is what prevents replay.
  • flower_sdk::crypto::webauthn::Authentication (a result) and flower_sdk::auth::Authentication (the hook mode) share a name: import one under another name if you need both.

Other primitives

  • NaCl (crypto.nacl()): secretbox, box, Ed25519 signing and detached signatures with explicit 24-byte nonces, SHA-512, and constant-time comparison, in NaCl's byte layouts.
  • Raw managed operations: managed_sign, managed_verify, managed_public_key and managed_version on any declared key, plus typed shortcuts for managed Ed25519 keys: sign, verify and public_key (which also reads an X25519 key).

There is no HMAC with a raw key (use a managed Hs256 key) and no JWKS fetching (guests have no network). Error codes: CRYPTO_ERROR, UNKNOWN_KEY, UNKNOWN_VERSION, FORBIDDEN_USAGE, KEYS_LOCKED (the member has no wrapping key mounted), KEY_REVOKED, KEY_DESTROYED, WEBAUTHN_COUNTER; see Error codes.
