Guides

Testing applications

Test guest logic natively against the real engine, without building Wasm or starting a server; test clients against a scripted transport; test workers against an in-memory queue; and keep a few end-to-end tests against a real node.

Guests in process

With the SDK's native-host feature, the engine can run your App directly as native Rust: same dispatch, same codecs, same host operations, same storage — no Wasm. Build the guest crate as an rlib too, as the quickstart does, so its tests can link it, and add two dev-dependencies:

Then deploy the module into an engine over a temporary file and call it, as the server would. This test runs the quickstart's module, building its calls from the argument structs and descriptors the attributes declared:

  • NativeRuntime::new(&APP) runs the app in-process; .manifest() is the manifest the Wasm build would embed. Add .with_crypto(…) for guests that use crypto.
  • invoke_mutation and invoke_query take definition names and values; failures come back with the guest's code. A descriptor's name and its argument struct's encode() keep the test in step with the module.
  • Calls name definitions directly, so a test can call what clients cannot — a timer's handler, a method without http. Set external: true in CallOptions (a MutationOptions carries one as call) to resolve the name as a client's HTTP call would.
  • CallOptions also sets credentials (to exercise the authorization hook), an asserted principal, a deadline, and a fixed timestamp_ms for time-dependent logic.
  • Native code is not sandboxed: a panic in your method panics the test, and Wasm limits (the instruction budget a method's deadline buys, memory) do not apply. Keep at least one test against the built Wasm.

Pure helpers — key building, validation, aggregate add/remove — are plain Rust: unit-test them directly.

Clients with MockTransport

flower_client::testing::MockTransport answers scripted replies in order and records every request:

pub async fn counts_with_a_mock() {
    use flower_client::testing::{MockReply, MockTransport};

    let mock = MockTransport::scripted([MockReply::ok(json!(3))]);
    let client = mock.client();
    let count = client
        .query_value("db", "app", "count", &json!({}), &RequestOptions::new())
        .await
        .unwrap();
    assert_eq!(count.value, 3);
    assert_eq!(mock.requests()[0].path, "/v1/query");
}

MockReply covers successes (ok), business failures (failure), HTTP errors (error), overload (overloaded), missing leaders (forward), server-sent event streams (events, event_stream) and hangs (hang, after the script runs out). Recorded requests expose their path, JSON body, headers and credentials, so you can assert on request IDs and deadlines.

Workers with FakeQueue

With flower-worker's testing feature, FakeQueue implements the queue protocol in memory, with the server's claiming rules — due order, scopes, priorities, fencing, leases, the waiter line and chained claims — on Tokio's clock, so tests can run in paused time:

pub async fn worker_against_a_fake_queue() {
    use flower_worker::testing::FakeQueue;

    let queue = FakeQueue::new();
    queue.enqueue("crm", "mail", json!({"to": "ada@example.com"}), 5);
    let stop = Arc::new(Notify::new());
    let worker = tokio::spawn(run_queue_worker(
        queue.clone(),
        QueueWorkerOptions::new("crm", "mail")
            .concurrency(1)
            .poll_interval(Duration::from_millis(10)),
        stop.clone(),
        |_claim| async move { Ok(()) },
    ));
    tokio::time::sleep(Duration::from_millis(200)).await;
    stop.notify_one();
    let summary = worker.await.unwrap().unwrap();
    assert_eq!(summary.completed, 1);
    assert_eq!(queue.stats("crm", "mail").pending, 0);
}

It can also refuse or fail polls and delay answers, to test backpressure and error paths. It does not model job names, groups or kept results.

End to end

For a few tests against the real thing, start a node in a temporary directory on free ports — --http 127.0.0.1:0 --raft 127.0.0.1:0 — and read the addresses it prints:

listening raft=127.0.0.1:52811
listening http=127.0.0.1:52812

Wait until /health/ready answers 200, deploy the built Wasm with cargo flower deploy or FlowerClient::deploy, and call it. Pass --timer-sweep-ms 100 to make timers fire quickly. Flower's own CLI tests (crates/cargo-flower/tests/cli.rs) work this way.

Every example in these docs is tested The guest snippets compile for wasm32, the client snippets compile natively, and the tests on this page run, from web/docs/examples in the repository.
