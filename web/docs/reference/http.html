Reference

HTTP API

Every member serves the same API on one port, over HTTP/1.1 and HTTP/2 (cleartext h2c, or h2 over TLS). Request bodies are JSON with Content-Type: application/json; answers are JSON unless noted. Every exchange on this page was recorded against a release node.

Endpoints

EndpointCredentialPurpose
POST/v1/querynone¹Run a query.
POST/v1/mutatenone¹Run a mutation.
POST/v1/transactionnone¹Run mutations in several databases atomically.
POST/v1/watchnone¹Watch a query (server-sent events).
GET/v1/retrynoneThe database's retry identity, for scoped request IDs.
POST/v1/retry/sessionnone¹Open, inspect, acknowledge and close retry sessions.
GET/v1/status, /health/live, /health/readynoneRaft status, liveness, readiness.
POST/v1/queue/…workerClaim, renew and report queue jobs.
GET/v1/timer/…adminInspect and maintain timers.
POST/v1/deploy, /v1/admin/…, /v1/metricsadminOperator endpoints.
GET/v1/syncsyncLog sync for device replicas (internal format).
GET/adminnone²The admin dashboard.

¹ The module's authorization component decides; see credentials. ² The page itself is static; it asks for the admin token to call the API.

Calls name a method by its HTTP name: the definition's name, for a definition whose declaration opts into HTTP (#[query(http)], Method::http(), Transaction::http(), an interface provider's COMPONENT.http(), external!(…, http)). Every other definition answers 404 UNKNOWN_METHOD here, whatever its access; see method options.

Credentials

Versioned machine-readable contracts are available as JSON Schema 2020-12, with valid and invalid golden fixtures. Select the appropriate named $defs schema for tokens, errors, discovery, watch frames and sync batches. The root validates call envelopes. Runtime checks additionally enforce causal, history and sync-coverage relationships.

Credentials travel as Authorization: Bearer <token> (exactly that capitalization). The server compares the token with its own three tokens:

  • The admin token unlocks operator endpoints and every worker and sync endpoint. On call endpoints it makes the caller a trusted gateway: the body may then carry principal ({"subject", "tenant"?, "claims"?}) and timestamp_ms (the clock the call reads), which are ignored otherwise. Watches honour principal and ignore timestamp_ms: they read the member's clock.
  • The worker token unlocks /v1/queue/…; the sync token unlocks /v1/sync.
  • Any other token is an end user's: it reaches the module's authorization component as {"bearer": "<token>"}. A call body (watches included) may instead carry credentials (any JSON), which takes precedence.

A wrong or missing server credential answers 403 {"ok":false,"code":"forbidden","message":"admin token missing or wrong"}. A token a server was not configured with authorizes nothing.

Headers

Request headers

HeaderApplies toMeaning
AuthorizationallBearer <token>; see above.
Content-TypeJSON bodiesMust be application/json: 415 unsupported_media_type otherwise.
x-flower-timeout-msallThe caller's deadline for the whole request, in whole milliseconds (capped at one day). It can only shorten a call's own deadline: a call cut off by it answers 503 caller_deadline_exceeded, requests still waiting for admission at it are refused with 503 overloaded, and a write still queued past it never runs. Followers forward what is left of it. For a watch it bounds the first snapshot only. Malformed: 400 bad_request.
x-flower-max-staleness-ms/v1/queryTightens a replica-local query's staleness bound (0–2147483647). 0 asks for a proven-fresh answer. Never loosens a query's own bound; ignored by linearizable queries. Malformed: 400.
x-flower-group (or ?group=)allRoute to a named group instead of the database's owner; mainly for operator endpoints of non-root groups. Unknown group: 404 unknown_group.
traceparentallW3C trace context, joined when OpenTelemetry export is on.

There is no header for request IDs (they go in the body as idempotency_key), for consistency (queries declare it), or for the database (it goes in the body or query string). A follower forwards Authorization, Content-Type, Accept, x-flower-max-staleness-ms and the remaining deadline to the leader, and no other header.

Version and capabilities

GET /v1/protocol returns {"version":1,"capabilities":["read_tokens","scoped_commands","watch_history","sync_since"]}. Responses report x-flower-protocol-version. Optional capabilities are checked explicitly; unknown required versions are refused.

Queries accept x-flower-at-least, an opaque scope-qualified read token. Successful queries report x-flower-read-token and x-flower-consistency; successful mutation envelopes may include read_token. Wrong-history read tokens answer 409 and malformed tokens 400. Token counters are canonical decimal strings. Never compare a database revision with a group log position.

Error bodies and terminal watch errors include a problem extension with status, code, message, details?, origin, execution, retryable and retry_after_ms?. Retry advice and outcome certainty are separate. Watch snapshots include history when established. Sync batches require version, since and their covered position.

Calls

POST /v1/query

Modules can expose request-time SQL through a normal query backed by SqlEndpoint. Its arguments typically contain statement and params; the module fixes the allowed collections, budgets and access rules. This uses the same query envelope and authentication as other methods. There is no generic /v1/sql route. See SQL queries.

FieldType
dbstringDatabase.
modulestringModule.
namestringThe query's HTTP name.
argsanyRequired; the method's arguments object ({} for none, or the bare value of a bare_arg method).
credentialsanyOptional; for the authorization component.
principal, timestamp_msTrusted gateway only.

Success is 200 {"ok":true,"value":<result>}, with no revision. A failure answers a non-2xx status with {"ok":false,"code","message","details"?}; the query's own failure is 422:

{"ok":true,"value":{"done":false,"title":"Buy milk"}}
{"code":"TASK_NOT_FOUND","details":"nope","message":"no task has this ID","ok":false}
{"code":"INVALID_ARGUMENT","details":{"path":["id"]},"message":"arguments for `task` invalid at $.id: expected string","ok":false}

Calling a mutation's name here answers 422 INVALID_INVOCATION; a name that is not a query or mutation with http in this module, or a module or database that does not exist, 404 UNKNOWN_METHOD.

POST /v1/mutate

The query fields, plus:

FieldType
idempotency_keystringThe request ID. A retry with the same key answers the recorded outcome. f1:/f2: keys are scoped IDs and must be well-formed (400 otherwise). See Retries.
expected_revisionintegerFail with stale_revision if the database has moved past it.
 
200 {"ok":true,"value":{"done":false,"title":"Buy milk"},"revision":1,"position":5,"duplicate":false}
200 {"ok":true,"value":{"done":false,"title":"Buy milk"},"revision":1,"position":5,"duplicate":true}
422 {"ok":false,"revision":1,"position":6,"code":"TASK_NOT_FOUND","message":"no task has this ID","details":"nope","duplicate":false}
422 {"ok":false,"revision":1,"position":8,"code":"stale_revision","message":"expected revision 0 but the database is at 1","duplicate":false}

Every outcome the mutation records answers with revision, position and duplicate: success with 200, and every failure — the method's own codes, INVALID_ARGUMENT, receipt refusals, access-policy refusals, stale_revision, a guest-side refusal such as queue_undeclared — with 422, the message and any details. Nothing the failed call wrote was kept; duplicate is true when a stored receipt answered. A mutation whose effects outgrow --max-transaction-bytes answers 413 transaction_too_large before anything is proposed. Calling a query's name here answers 422 INVALID_INVOCATION.

POST /v1/transaction

{
  "steps": [
    {"db": "demo",    "module": "tasks", "method": "complete_task", "args": {"id": "milk"}},
    {"db": "archive", "module": "tasks", "method": "add_task",      "args": {"id": "milk", "title": "Buy milk"}}
  ],
  "idempotency_key": "archive-milk"
}

At least one step, each on a different database (422 INVALID_VALUE otherwise); method is a mutation's HTTP name. Also takes credentials and the gateway fields. The steps share one deadline (60 s, shortened by x-flower-timeout-ms), and their committed effects are bounded by --max-transaction-bytes (413 transaction_too_large). The answer is the mutation shape with value as an array of step results, plus revisions (per database) and, across groups, positions (per group):

200 {"ok":true,"value":[{"done":true,"title":"Buy milk"},{"done":false,"title":"Buy milk"}],"revision":4,"position":14,"revisions":{"archive":1,"demo":4},"duplicate":false}
422 {"ok":false,"revision":4,"position":0,"code":"TASK_NOT_FOUND","message":"no task has this ID","details":"zzz","duplicate":false}

A failing step answers 422 with that step's failure; nothing committed. See Transactions.

POST /v1/watch

The body is exactly a query's — db, module, name, args, credentials?, principal? (trusted gateway) — plus "deltas": true to accept patch events:

curl -sN http://127.0.0.1:8080/v1/watch -H 'content-type: application/json' \
  -d '{"db":"demo","module":"tasks","name":"open_tasks","args":{},"deltas":true}'

A failure before the first snapshot answers an ordinary JSON error, with the query's status (422 for its own failure). Then text/event-stream:

event: snapshot
data: {"revision":3,"id":1,"value":[{"id":"bread","title":"Bake bread"}]}

event: patch
data: {"revision":4,"id":3,"base":2,"patch":[{"op":"add","path":"/0","value":{"id":"eggs","title":"Buy eggs"}}]}

event: error
data: {"code":"unauthorized","message":"…"}

: watching
  • snapshot carries a whole value; it is always first. patch (with deltas) applies RFC 6902 add/remove/replace operations to the value whose id is base, whenever the patch is smaller than the value.
  • error ends the stream: unauthorized, watch_scope_changed, shutdown, forward, overloaded, the query's own failure (with its details, if any), UNKNOWN_METHOD after a redeploy, partition_moving, and others. Reconnect for a fresh snapshot.
  • : watching comments keep idle streams open every 15 s. There are no id: fields and no resume.
  • Later refreshes run on the member's clock, without the subscribing request's deadline. Subscribers are reauthorized at least every 30 s.
  • A subscriber more than 32 events behind is disconnected without an error event. The member holds at most 64 MiB of watches' arguments and credentials; past it a new watch answers 503 overloaded.

GET /v1/retry, POST /v1/retry/session

GET /v1/retry?db=D answers the database's retry identity — incarnation, epoch, min_epoch, epoch_ms, keep_epochs, initialized and counters — from which clients mint f1: and f2: request IDs. POST /v1/retry/session takes {"db","module","session":"<32 hex>","operation":"open"|"status"|"ack"|"close","through"?,"abandon"?,"limit"?,"credentials"?} and answers {"ok":true,"session":{session,incarnation,epoch,acknowledged,closed}}. The module's authorization component decides the session's owner under its sessions access.

Status and health

GET /v1/status     {"id":1,"state":"Leader","leader":1,"term":1,"last_log":14,"last_applied":14}
GET /health/live   {"ok":true}
GET /health/ready  {"applied":14,"committed":14,"leader":1,"ok":true,"reason":null,"rejoining":false,"storage":null}

/health/ready answers 503 with a reason (no known leader, applying committed entries, rejoining: …, a storage failure) when the member should not take traffic; ?group= asks about one group.

Queues

Worker or admin token. Every answer is 200: {"ok":true,…}, or {"ok":false,"code","message"} for refusals such as a lease no longer held, or queue_purging while a removed module's queue is being deleted (retry once the purge ends). Native workers may name any queue; guests use only the queues their module declares.

EndpointBody or parametersAnswer
POST/v1/queue/poll{db, queue, limit?=10, lease_ms?=30000, scope?="", owner?, wait_ms?}items: claims with id, token, payload, attempts, fence, scope, priority, owner, name, group, expires_ms, available_ms, claimed_ms
POST/v1/queue/heartbeat{db, queue, id, token, lease_ms?}renews the lease
POST/v1/queue/complete{db, queue, id, token, result?, next?}with result, keeps the job completed; without, deletes it; next claims more in the same commit
POST/v1/queue/fail{db, queue, id, token, delay_ms?, next?}pending again, or dead when attempts are spent
POST/v1/queue/kill{db, queue, id, token, next?}dead now
POST/v1/queue/release{db, queue, id, token, delay_ms?}pending again, attempt not spent
POST/v1/queue/cancel, /retry, /purge{db, queue, id}, {db, queue, id, delay_ms?}, {db, queue, older_than_ms?}delete a job; revive a dead one; delete old dead and completed jobs
GET/v1/queue/stats, /ready, /item?db&queue&scope&owner; /item takes id, or name and scopecounts (pending, claimed, dead, completed, ready, next_ms) and readiness; one job

next is a claim: {limit?, lease_ms?, scope?, owner?, wait_ms?}.

Timers

Admin token. GET /v1/timer/stats?db (pending, dead, held), GET /v1/timer/get?db&id, GET /v1/timer/list?db&state=pending|dead|held|all&limit; POST /v1/timer/cancel {db, id}, /retry {db, id, delay_ms?}, /purge {db, older_than_ms?}. A held timer came due while its module was removed. Timers fire from the leader's maintenance loop, not from an endpoint.

Errors

Every error answers JSON: {"ok":false,"code":…,"message":…}, with details when the call's own failure carries any, revision/position/duplicate for a recorded write, retry_after_ms for retryable refusals and leader for forward. The status tells a client what to do; only 422 is the call's own answer.

415unsupported_media_typeNo
