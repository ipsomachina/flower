Reference

flower-sdk

The guest SDK: no_std plus alloc, no runtime dependencies. This page lists its public surface by module; the concept pages explain how the pieces fit.

Crate setup

  • A guest is a cdylib built for wasm32-unknown-unknown; add "rlib" so tests and Rust clients can link its types and descriptors (Testing, typed calls).
  • The derive and attribute macros generate ::flower_sdk and ::alloc paths: put extern crate alloc; at the crate root.
  • Guests may use std types that only allocate; operating-system APIs (files, sockets, threads, clocks) are not available.
  • End the crate with flower_sdk::export!(APP);.

Application assembly

#[interface] also accepts client = ClientName to generate native query methods, prepare_* methods and command builders. See generated workflows.

#[flower_sdk::application] on an inline module generates its public APP catalogue from lexical collection and method declarations. Mark additional component statics, such as SQL plans, endpoints or component arrays, with #[component]. Export it explicitly with flower_sdk::export!(module::APP). HTTP exposure and access rules stay explicit on the methods. App::new remains available for custom initialization and composition. See the compiled SQL example.

sql

SqlQuery<P, R> is a registered, deployment-checked statement with typed parameters and rows. SqlEndpoint is a registered capability for request-time SQL over an explicit collection allowlist. Both use SqlBudget::new(candidates, bytes, work) (scan remains available), and offer require_index, run, explain and explain_typed. Endpoints additionally provide run_as<R> and accept any FlowerType parameter object. SqlExplain exposes common fields and retains the original response in raw.

SQL executes with the enclosing invocation's snapshot, staged writes, authority and policies. Neither declaration creates an HTTP alias. Results have no continuation cursor. See SQL queries for supported syntax, limits and examples.

Absent and nullable members

Nullable<T> is a required member whose visible value may be null. Omittable<T> is either Missing or Present(T); Omittable<Nullable<T>> represents absence, explicit null and a value separately. Encoding omits missing fields, and decoding preserves the distinction. Field<T> continues to represent policy redaction. Legacy method Option parameters retain their omission default; ordinary Option struct fields remain required.

#[interface(name = "tasks.v1", handle = TasksApi, client = TasksClient)] optionally generates a native facade with named query methods and prepare_* mutation methods. Bind it with TasksApi::client(remote). The facade uses flower_sdk::remote::RemoteModule; the SDK remains independent of HTTP, Tokio and provider implementations. Query builders and preparation futures are chosen by the backend, preserving native result metadata. The macro reports collisions between generated method names at the contract.
