cargo flower

One binary, cargo-flower, builds and inspects guests, deploys and calls them, operates clusters, and serves cluster nodes. Run it as cargo flower <command> or cargo-flower <command>.

Conventions

  • Install with cargo install --path crates/cargo-flower from a Flower checkout. --help works on every command and subcommand.
  • Commands that talk to a server take --endpoint URL (http:// or https://), read from FLOWER_ENDPOINT when absent, and default to http://127.0.0.1:8080. HTTPS trusts the platform's roots. (backup is the exception: it talks to a server only when given an endpoint.)
  • Credentials: operator commands take --admin-token or FLOWER_ADMIN_TOKEN; call, transaction and retry take --token or FLOWER_TOKEN (an end user's token for the module's authorization component, or the admin token as a trusted gateway); queue takes --token or FLOWER_WORKER_TOKEN.
  • Flags of a command come before its subcommand: cargo flower queue --db app stats --queue mail, not queue stats --db app ….
  • Output is key=value lines or JSON, depending on the command. Errors print cargo-flower: <message> to stderr and exit 1; usage errors exit 2. The CLI does not retry; each request has a 20-second timeout.
export FLOWER_ENDPOINT=https://flower.example.com FLOWER_ADMIN_TOKEN=…
cargo flower status

Building and inspecting

build

cargo flower build [--package P] [--manifest-path Cargo.toml] [--profile release] \
  [--features a,b] [--no-default-features] [--locked] [--out-dir .flower]

Builds the workspace's cdylib (exactly one, or the one --package names) for wasm32-unknown-unknown, inspects it through the server's Wasm backend, and writes <package>.wasm and <package>.manifest.json. Prints built <name> wasm=… manifest=… sha256=… and counts of collections, queries, mutations, derived values, transactions, triggers, HTTP names, SQL plans and SQL endpoints.

dev

cargo flower dev --package P --db D --module M [--watch .] [--endpoint URL] [--once]

Watches Rust sources, Cargo manifests and lockfiles beneath the selected Cargo workspace directory, builds with the dev profile and deploys successful builds to a running server. It uses the ordinary deployment preflight and FLOWER_ADMIN_TOKEN. --once performs one build/deploy cycle and returns its status. Otherwise failures wait for a source edit; Ctrl-C stops the watcher. Symlinks and directories named target, .git and .flower are excluded.

plan

cargo flower plan --wasm W [--manifest M] [--current DEPLOYED] [--module NAME] \
  [--with MODULE=FILE]… [--bind SLOT=MODULE]… [--bindings FILE]

Preflights a deployment offline: validates the module and manifest, applies bindings, prints the content identity, diffs against --current (a manifest or Wasm), and with --with runs the cross-module link check. Exits 1 on an incompatible change.

contract

cargo flower contract inspect --manifest M
cargo flower contract diff --from OLD --to NEW
cargo flower contract typescript --manifest M --out contracts.ts

inspect prints collections, indexes, references, definitions and triggers. diff marks lines + added, - removed, ~ changed and ! incompatible; it always exits 0.

Inspection and diff also include named SQL plans and scoped endpoints. typescript generates deterministic Queries and Mutations wire-type maps for public aliases, including argument, result and error contracts. Decimal integers remain strings; optional and nullable fields remain distinct. These static types require server validation for bounds, patterns and authorization.

sql-explain

cargo flower sql-explain --manifest M --plan PLAN

Explains a named SQL plan offline, including its access path and budgets. For dynamic SQL, call the module's explain query. See SQL queries.

Deploying

deploy

cargo flower deploy --db D --module M --wasm W [--manifest M] [--identity HEX] \
  [--bind SLOT=MODULE]… [--bindings FILE] [--endpoint URL] [--admin-token T]

Runs the plan preflight, then deploys through consensus. Prints revision=… position=…. A slot the module imports ($inventory) must be bound, or nothing is sent.

modules

cargo flower modules [--db D] [list]
cargo flower modules --db D remove --module M [--purge]

list prints one line per module: its identity, definition count, collections, HTTP names (http=), whether it has an authorization component and any staging. remove takes the module's code, HTTP names, hooks and derived values away and keeps its data; --purge deletes the data too, a page at a time, and the module cannot deploy again until the purge ends.

Calling

call

cargo flower call --db D --module M --name NAME [--args JSON | --args-file FILE] \
  [--contract MANIFEST] [--mutation [--request-id ID]] [--token T]

--args-file - reads JSON from standard input. File input and inline --args are mutually exclusive. --contract checks the public alias, requested operation kind and structural argument schema before delivery. Host-only validations and authorization remain server checks.

--name is the method's HTTP name: only methods that declare http answer. Add --mutation for a mutation. Without --contract, a kind mismatch is rejected by the server; with a contract, it is rejected locally. Prints the result as JSON; a mutation also prints revision=… position=… duplicate=…. --request-id makes a retry answer the original outcome while the server retains that receipt.

transaction

cargo flower transaction --steps '[{"db","module","method","args"}, …]' [--request-id ID] [--token T]

retry

cargo flower retry --db D [--token T]                       # the retry identity, as JSON
cargo flower retry --db D id --intent order:42              # an f1: request ID
cargo flower retry --db D open --module M [--session HEX]   # a retry session
cargo flower retry --db D session-id --module M --session HEX --sequence 1
cargo flower retry --db D ack --module M --session HEX --through N [--abandon] [--limit N]
cargo flower retry --db D status|close --module M --session HEX

keys

Every database keeps its own replicated key catalog. Without a subcommand (or with list), keys prints every database's catalog, or one with --db; changes need --db (before or after the subcommand, as --request-id) and run at the leader of the database's group under a request ID (printed when you pass none; pass --request-id to retry one safely).

A change sent to a member started without --key-wrapping-file answers 503 KEYS_LOCKED (retry once a member with the key leads): retries exhausted: status 503 KEYS_LOCKED: no wrapping key is mounted. See Guest cryptography.

backup list and restore

cargo flower backup list --backup-url s3://BUCKET/PREFIX --keystore KS --kek-file KEK
cargo flower backup restore --backup-url s3://BUCKET/PREFIX --keystore KS --kek-file KEK --dir data \
  [--at-ms MS | --index N [--history H] | --manifest NAME]

Both run offline, against --backup-url (s3://… or file:///…, or FLOWER_BACKUP_URL) or --backup-dir, configured as for serve. Without a target, restore restores the newest state the backups hold (the latest base, then the archive after it); --manifest restores one backup as it was taken. restore replaces a stopped node's group file and removes its Raft log; start the node with --bootstrap afterwards. For an existing cluster, stop every member and restore the same target on each. See Backups.

serve

Serves a cluster node: Raft plus the HTTP API. Only --dir and --id are required. Most flags also read an environment variable, shown in the tables; restarting with the same flags is always safe.

cargo flower serve --dir data --id 1 --bootstrap 1 --admin-token secret

Upgrades across a compatibility contract A member's files record the storage contract they were written under (how entries apply, how snapshots and values encode). A build whose contract differs refuses to open them at start (incompatible_store), naming both, and refuses peers of another contract. There is no in-place migration: across a contract change, take a backup, then restore it into a fresh directory under the new build. Builds that keep the contract roll one member at a time.
