Flower documentation

Flower's code and documentation are open source under the MIT license.

Flower is a replicated database of source records and reactive derived values. You write the application logic in Rust, compile it to WebAssembly, deploy it into a cluster, and call it by name over HTTP.

Explore Flower’s source and examples in the GitHub repository. These docs cover the current implementation.

These pages are for developers building applications on Flower: writing guest modules with flower-sdk, deploying them with cargo flower, calling them from any HTTP client or from Rust with flower-client, and running the native workers and clusters that serve them. Read them top to bottom the first time — the quickstart, then the concepts, then the guides — and come back to the reference.

The shape of an application

A Flower application is a module: a Rust crate built as a wasm32-unknown-unknown cdylib. Each operation and record type is declared once, with everything about it, and one static App::new(&[…]) lists the module's components:

  • Collections of typed records, with indexes and references the engine maintains for you.
  • Queries, which read, and mutations, which read and write. Both are plain synchronous Rust functions, each declaring its own name, consistency, access and deadline.
  • Derived values and aggregates: computations the engine caches, tracks the dependencies of, and keeps current as records change.
  • HTTP exposure, opted into per operation: nothing answers over HTTP unless its declaration says http.
  • Components such as an authorization component, queues, triggers, maintenance tasks, managed keys, and imports of other modules' exports.

When a client calls a mutation, the leader runs your Rust function inside an isolated WebAssembly instance. Every read it makes is tracked and every write is staged. When the function returns, the engine validates the staged writes against your schemas, references and access rules, updates indexes and the derived values that depended on what changed, and commits all of it as one entry in the Raft log. Followers apply that entry; they never re-run your code. A query reads one consistent snapshot. A watch keeps a query's result up to date as the records it read change.

Work that must leave the database — sending email, charging a card, calling another service — goes through durable queues that native Rust workers claim under fenced leases, and through timers that fire mutations later. Guests themselves never open sockets.

What Flower guarantees

  • Atomic mutations. A mutation's writes, the index entries they imply and the derived values that must change with them are published together, or not at all.
  • Linearizable reads by default. A query declared Linearizable sees every write that completed before it began, whichever member serves it. Queries can opt into cheaper replica-local reads, with or without a staleness bound.
  • Exactly-once effects for retried writes. A mutation sent again with the same request ID answers the original outcome instead of running twice — see retries and receipts.
  • Isolation between modules. A module exports nothing unless it says so; another module can read only what it exports and can never write its collections directly.
  • Bounded guests. Every invocation runs under memory and stack limits and the deadline its method declares; a runaway guest fails its own call, never the process, and whether a call fits its budget does not depend on which member runs it.

The crates you will use

CrateWhere it runsWhat it is for
flower-sdkYour guest (Wasm)Types, schemas, collections, contexts and components for writing modules. no_std plus alloc, no runtime dependencies.
cargo-flowerYour machine, your serversThe cargo flower command: build and inspect guests, plan and deploy them, call methods, and serve a cluster node.
flower-clientNative RustAn HTTP client with retries, deadlines, watches, transactions and admin calls, which calls methods type-checked through the descriptors your guest crate declares.
flower-workerNative RustQueue workers with leases, concurrency control and graceful draining, and the reconcile worker for external values.

The Flower repository also carries complete example guests in examples/: goblin-pizza (orders, an aggregate, oven timers and a delivery queue), crypto-ticket (signed tickets under a managed key), external-transactions and the typed-modules-* trio (a provider and a consumer linked through an interface crate). These docs quote them often.
